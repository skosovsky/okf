# 006 — Создание нового bundle через Go CLI

Статус: backlog. Приоритет: P1. Источник: исследование `scaccogatto/okf-skills`, commit `68ce7a0c07f66ca9a6b0beb68937d75314d5e8a5`.

## Проблема и результат

CLI умеет читать, проверять и изменять существующие bundles, но не даёт короткого пути от пустого каталога к первому concept. Добавить scaffolding в существующий Go CLI и переносимые инструкции для агентов.

Reference: [upstream init](https://github.com/scaccogatto/okf-skills/blob/68ce7a0c07f66ca9a6b0beb68937d75314d5e8a5/skills/okf/scripts/okf_init.py). Переносится сценарий, не Python-код.

## Контракт до реализации

- Описать предлагаемую команду `okf init <directory>`: файлы, stdout/JSON, ошибки, exit codes и поведение при повторном запуске. Это проект API, команды пока нет.
- Bundle path явный; не занимать автоматически `.okf`, служащий private namespace store относительно bundle root.
- Минимальный результат: root `index.md` с declaration и один concept с непустым `type`. Наличие log и ознакомительного concept определить в контракте.
- Сначала выбрать target spec revision по задаче 004. Полнота optional metadata не является обязательным условием scaffolding.
- Не изобретать sources/verification. Для собственного созданного шаблона допустим известный process actor, но не автор импортированного содержания. Placeholder явно маркировать `draft` как producer policy.
- Непустой каталог, конфликты имён, symlinks и повторный запуск должны иметь явное недеструктивное поведение. Не вводить общий `--force`, молча перезаписывающий знания.
- Определить публикацию нового каталога и гарантию отказа: нельзя создавать полупустой bundle при ошибке посередине. Переиспользовать существующие Go publication primitives после проверки их применимости к отсутствующему root; не строить второй journal.
