## A. Исправить подтверждённые дефекты viewer

### A1. Legacy-источники пропадают из панели Sources

В `viewer/viewer.go` сбор источников через `Frontmatter.SourceStatesForProfileContext` не учитывает legacy `# Citations`. На существующей fixture `fixtures/v02/compat/declared-v01` парсер возвращает одну цитату, projection — ноль Sources, UI пишет `No sources recorded.` Цитата остаётся в основном тексте; дефект касается структурированной панели и неверного сообщения.

Использовать существующую эффективную модель provenance с presence-only fallback. При наличии YAML `sources`, включая malformed replacement, не подмешивать legacy citations. Не изобретать merge/dedup, источник или verification. Представление legacy-записи без URL должно сохранять доступный текст без выдуманного адреса. Сначала закрепить представление в контракте viewer, затем исправить код.

### A2. Допустимые ConceptID совпадают с namespace сносок

В `viewer/assets/viewer.js` ранний `return` для `/^fn(?:ref)?:/i` после декодирования hash блокирует допустимые ID `fn:example` и `fnref:example`. Загрузка и экспорт проходят; прямой переход даёт пустую карточку, переход из другой карточки может оставить старую.

Разрешать существующий ConceptID до обработки anchors либо ввести совместимое разделение маршрутов. Сохранить существующие deep links, percent-encoding и работу настоящих footnotes. Проверить прямое открытие, клики и Back/Forward в браузере. Node/DOM stub сам по себе не заменяет браузерную приёмку.

Исходные временные репро находились в `/tmp/okf-audit-repro.go` и `/tmp/okf-audit-viewer.cjs`; на их сохранность не полагаться. Добавить постоянные regression fixtures/tests в принятые в репозитории места.

## C. Поиск по разделам — сначала контракт

Текущий `search_concepts` — контракт буквальной подстроки. Не менять его семантику молча. Спроектировать additive CLI/MCP-поверхность поверх общего Go query layer; конкретные новые имена закрепить в документации и JSON Schema до реализации.

Минимальный новый контракт:

- Lexical search по нескольким словам с ранжированием BM25 или явно описанным эквивалентом; определить Unicode/case normalization, tokenization, AND/OR и tie-breaks. Не обещать понимание синонимов и переводов.
- Единица результата — раздел Markdown из существующего parser/AST. Возвращать concept ID, путь, заголовок/locator, snippet, диапазон строк, основание ранжирования и revision/content digest. Явно определить нумерацию строк относительно исходного файла и поведение при изменении файла после поиска.
- Определить caps запроса, загрузки, числа результатов и размера ответа, ошибки и cancellation. Указать `total/truncated` и способ продолжения либо честное ограничение выдачи; скрытая потеря данных недопустима.
- Сохранять root containment, запрет symlink escape и инертность содержимого. Trust/status/staleness не выводить из score; без reference time не придумывать свежесть.
- CLI и MCP используют одинаковую семантику и ранжирование. Существующие tools, graph formats и conformance остаются совместимыми.
- Индекс, если нужен, является производным и восстанавливаемым; Markdown остаётся источником истины. Выбрать минимально достаточную реализацию, не вводить обязательный внешний сервис, embedding provider или новую фиксированную таксономию.

Проверки включают русский и английский текст, слова в разных частях раздела, пустой запрос, no-hit, ties, необычные IDs, изменения исходника, code fences, лимиты и отмену.

## Два независимых субагента и цикл исправлений

После реализации запустить двух отдельных субагентов на одном состоянии файлов. Передать задачу, baseline, diff и пути к evidence; каждый сам проверяет источники. Они не редактируют продукт и не видят выводы друг друга до первого заключения.

1. **Полнота.** Проверить AC01–AC19 и обязательные детали A–E. Вернуть таблицу `ID → выполнено/не выполнено → файл/команда/artifact → пробел`, процент и список блокеров. До второго заключения AC20 остаётся pending, максимум 95%. После обоих ревью основной агент фиксирует evidence; ревьюер полноты повторно проверяет AC20 и выдаёт окончательный процент.
2. **Ошибки.** Искать реальные дефекты, регрессии, несоответствия схемам, потерю данных, неверные claims и сбои первого запуска. Проверять adversarial cases. Для каждого замечания: severity, файл/строка, сценарий, expected/actual, последствия и способ проверки исправления. «Ошибок не найдено» должно перечислять охваченные области и ограничения, не обещать абсолютного отсутствия ошибок.
3. **Исправление.** Основной агент устраняет пробелы и подтверждённые дефекты всех приоритетов в scope, выполняет затронутые проверки. Замечание можно снять с доказательством и подтверждением автора; нельзя просто перенести его в backlog ради закрытия.
4. **Повторное ревью.** Оба субагента проверяют итоговое состояние после исправлений и влияние правок на предыдущие критерии. Повторять до 100% и отсутствия открытых подтверждённых замечаний.
