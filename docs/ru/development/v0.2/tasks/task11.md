# Валидатор OKF v0.2 с учётом версии {#section001}

> Исторический документ. План сохранён из ревизии исходника `61e75e9` и не является текущим руководством по реализации. [Исходный документ](https://github.com/skosovsky/okf/blob/61e75e9/docs/development/v0.2/tasks/task11.md).

## 1. Цель {#section002}

Добавить базовую и строгую политики с учётом версии для OKF v0.1 и v0.2 без
расширения обязательных требований соответствия за пределы §11.

Зависимости: [`task09.md`]({{ '/ru/development/v0.2/tasks/task09/' | relative_url }}), [`task10.md`]({{ '/ru/development/v0.2/tasks/task10/' | relative_url }}).

## 2. Политика версий {#section003}

| Целевая версия | Базовая проверка | Строгая проверка |
| --- | --- | --- |
| `0.1` | существующий контракт | старые `timestamp`/`# Citations` |
| `0.2` | §11 | группы полей v0.2 и рекомендации для вычислений |
| отсутствует | v0.2 + резервные правила §13 | проверка присутствующих групп полей |
| будущая | по мере возможностей | только безопасное известное подмножество |

Определение версии должно быть общим доменным API, а не локальной эвристикой
валидатора.

## 3. Контракт уровней диагностики {#section004}

`ERROR`:

- некорректные или отсутствующие метаданные концепта;
- отсутствующая или пустая строка `type`;
- некорректная структура зарезервированного файла.

`WARNING` — только в строгом режиме или при проверке политик:

- некорректная присутствующая группа полей v0.2;
- целостность связи источников и сносок;
- некорректный жизненный цикл или актуальность;
- непригодный контракт Attested Computation;
- граница устаревания.

Отсутствующие необязательные группы, неизвестные типы, ключи и среды выполнения,
нерабочие ресурсы и пути не являются ошибками соответствия.

Каждая новая диагностика получает стабильный `Code`, файл и точный путь поля,
например `sources[2].resource`.

## 4. Строгая проверка групп полей {#section005}

### Источники {#section006}

- `sources` — последовательность отображений.
- `resource` обязателен и является непустым скаляром в каждой записи.
- `id`, `title`, `author` проверять при наличии.
- Уникальность ID — политика атрибуции инструментария.
- `usage_count` — неотрицательное целое число в профиле инструментария.
- Действующее `usage_window` содержит `from/to`, корректные даты и `from <= to`.
- `usage_count` требует действующего окна.
- Сноски источников сопоставляются по ID; блоки кода игнорируются.
- `sources[].resource` может быть описанием области.
- `sources[].author` проверять только как непустую строку из-за неоднозначности
  исходной спецификации `team:*`.

### Генерация и проверки {#section007}

- `generated` — отображение; `by` обязателен внутри присутствующего отображения;
  `at`, если есть, соответствует RFC3339.
- Соглашение об участниках применять к `generated.by`/`verified.by`.
- `verified` принимает отображение и последовательность.
- Каждое событие содержит `by/at`; одиночное отображение нормализуется.
- Уровень доверия вычисляется и никогда не хранится.
- Переход к старому `timestamp` разрешён только при полном отсутствии `generated`.

### Жизненный цикл {#section008}

- `status`: `draft|stable|deprecated`, отсутствие → `stable`.
- `stale_after`: корректная дата `YYYY-MM-DD`.
- Опорная дата внедряется; `today == stale_after` означает устаревание.

### Поля со значениями путей {#section009}

Поддержать абсолютные URL, пути относительно `bundle` и относительные пути для:

- `resource`;
- `computation`;
- `executor.resource`;
- `attester.resource`.

Не проверять сеть и существование целевого объекта как требование соответствия.

## 5. Attested Computation {#section010}

Для точного значения типа:

- `runtime` непустой; неизвестные значения разрешены;
- параметры — отображения `{name,type,required}` с уникальными именами и
  логическим `required`;
- вычисление задано встроенным кодом либо путём, но не обоими способами;
- встроенный режим — один блок кода под заголовком верхнего уровня `# Computation`;
- структуры `executor`/`attester` проверяются при наличии;
- `receipt` — уникальные непустые имена полей.

Отсутствующие `runtime`/`computation`/`executor`/`attester` остаются предупреждениями
строгого режима, а не ошибками базового. Отложенный ABI не проверять.

## 6. Резервное чтение старого формата {#section011}

- Явная v0.1 сохраняет старые строгие правила.
- Потребитель v0.2 читает `timestamp`/`Citations` только при отсутствии замены.
- Числовое `[1]` в явно указанной v0.2 не включает политику старого формата
  автоматически.
- Резервное чтение не переписывает документ и не создаёт предупреждение только
  из-за старой формы представления.

## 7. Тестовые данные и тесты {#section012}

Добавить группы `v02/positive`, `v02/strict`, `v02/compat`,
`v02/adversarial`.

Покрыть:

- минимальный концепт только с `type`;
- приложение A;
- `verified` в виде отображения и списка;
- локальные и относительные ресурсы, описания области;
- некорректную структуру каждой группы;
- повторяющиеся ID, сноски без источника, блоки кода;
- варианты участников;
- некорректные временные метки, даты и окна;
- устаревание до границы, на границе и после неё;
- варианты параметров и вычислений;
- объявленную 0.1, отсутствие версии, 0.2, будущую версию;
- неявные временные метки и даты YAML;
- некорректная необязательная группа → предупреждение, `ErrorCount == 0`.

Все тесты — AAA, вывод детерминированный.

## 8. Критерии приёмки {#section013}

- Официальные примеры v0.2 соответствуют базовым требованиям.
- Канонические данные приложения проходят строгую проверку без диагностик.
- Регрессионные данные v0.1 проходят проверки.
- Документ только с `type` остаётся соответствующим требованиям.
- Одиночный `verified` равнозначен списку из одного элемента.
- Нет ложного предупреждения об отсутствующем `timestamp` в v0.2.
- Коды и пути полей стабильны.
- `go test ./validator ./bundle` и `go test ./...` проходят.

## 9. Вне рамок задачи {#section014}

Выполнение, ABI квитанций и вердиктов, среда выполнения, песочница и кеш `attester`,
привязка для конкретной среды выполнения, сетевые проверки и миграция.
