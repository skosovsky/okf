# Справочник OKF

Этот раздел описывает правила toolkit после [первого запуска]({{ '/ru/quickstart/' | relative_url }}). Полные подробности прежнего README, включая точные коды ошибок, схемы и гарантии миграции, сохранены в [английском справочнике]({{ '/reference/' | relative_url }}).

## Формат и версии

Нормативный документ — [зафиксированная спецификация v0.2](https://github.com/skosovsky/okf/blob/main/skills/open-knowledge-format/references/spec-v02.md). Формат OKF и версия программы независимы:

- `0.2` — текущий контракт чтения и записи.
- `0.1` — поддерживаемый старый формат для чтения, проверки и явной миграции.
- Неизвестные будущие версии сохраняются; программа читает знакомые ей данные и не заявляет полного соответствия неизвестному контракту.

Версия документов задаётся через `okf_version` только в корневом `index.md`. При отсутствии поля используется v0.2. Повреждённое значение не считается отсутствием: это ошибка структуры индекса. Явный выбор версии в команде — утверждение; конфликт с объявлением в наборе знаний приводит к ошибке.

Два зафиксированных upstream-документа называются `0.2`, но различаются правилами времени. По умолчанию применяется `date-3fcbb9f`; профиль `instant-0b87c52` сравнивает точные моменты с часовым смещением. Преобразование календарной даты в момент требует явной политики часового пояса. См. [решение о профилях](https://github.com/skosovsky/okf/blob/main/docs/adr/0003-okf-v02-temporal-revisions.md).

## Проверка структуры

Каждая заметка — UTF-8 Markdown с корректными метаданными YAML и непустой строкой `type`. `index.md` и `log.md` имеют отдельные правила структуры. Неизвестные типы и ключи сохраняются, а необязательные сведения об источниках, проверках, состоянии и вычислениях можно не указывать.

Проверки разделены:

| Проверка | Что означает |
| --- | --- |
| Базовая | Файл соответствует обязательной структуре формата. |
| `--strict` | Рекомендации по присутствующим необязательным полям. |
| `--check-links` | Диагностика внутренних ссылок. |
| `--check-orphans` | Диагностика заметок, не перечисленных в индексах. |

Успешная проверка формата не доказывает фактическую истинность текста. Примеры и полный контракт — в [руководстве по библиотекам]({{ '/ru/toolkit/' | relative_url }}).

## Источники, автор и проверки

`sources` описывает предоставленные материалы. Сноски в тексте ссылаются на `sources[].id`. `generated` указывает известного производителя текущего текста. `verified` фиксирует отдельные выполненные проверки.

При чтении старых документов:

- `timestamp` используется только при полном отсутствии `generated`.
- `# Citations` используется только при отсутствии `sources`.
- Даже повреждённое присутствующее замещающее поле запрещает подстановку старого значения.
- Одиночное значение `verified` приводится к списку из одного элемента.

Проверенность выводится только из `verified`: отсутствие означает `unverified`, проверки только машиной — `machine-confirmed`, наличие проверки `human:<id>` — `human-reviewed`. Авторство человека само по себе не является проверкой.

Проверенность, `status` и устаревание — разные сведения. Ни Git, ни время файла, ни миграция не создают подтверждение достоверности или свежести. При одновременном наличии `sources` и старых цитат чтение предпочитает v0.2, сохраняя исходные данные. Миграция требует ручного разрешения этого конфликта.

## CLI и Go API

Основной путь: `okf init`, `okf validate`, `okf info`, `okf view`. `init` создаёт только отсутствующий каталог с существующим родителем; `view` пишет новый файл вне набора знаний. Дополнительные команды: `parse`, `fmt`, `index`, `graph` и `migrate`.

```sh
okf version
okf validate --path ./knowledge --spec auto --strict --as-of 2026-09-26
okf info ./knowledge --spec auto --as-of 2026-09-26
```

Публичные пакеты: `bundle`, `validator`, `graph`, `mutation`, `store`, `store/fs`. Можно использовать собственные типы; типизированные представления v0.2 не уничтожают неизвестные ключи YAML. Пример Go и полный перечень команд — в [английском справочнике]({{ '/reference/' | relative_url }}).

## MCP и согласованные изменения

Сервер предоставляет 14 инструментов, включая `search_sections` для поиска по нескольким словам в разделе. См. [контракт поиска]({{ '/contracts/section-search/' | relative_url }}).

[Подключение MCP]({{ '/ru/getting-started-mcp/' | relative_url }}) показывает один клиентский сценарий. Сервер запускается без `-root`: каждый запрос указывает доступный абсолютный `bundle_path`. Какие пути доступны, определяют разрешения клиента и процесса.

`search_concepts` ищет буквальное совпадение, `read_concept` читает документ, `get_neighbors` возвращает связи. Ответы ограничены; `total` и `truncated` сообщают об усечении, курсора у этих запросов нет. Ошибка `resource_limit` не является частичной страницей. См. [контракт запросов]({{ '/contracts/concept-queries/' | relative_url }}).

Изменения проходят через пары preview/apply. Применение правки требует `expected_revision` и digest просмотренного плана. Предпросмотр не даёт разрешения на запись. После сбоя связи во время применения исход может быть неизвестен: сначала проверьте данные и повторите тот же запрос. Actor в метаданных описывает автора и не является аутентификацией пользователя.

Счётчик `usage_count` передаётся канонической десятичной строкой, чтобы избежать потери точности. Правила выбора источников для `set_usage_window` и `remove_source`, ограничения actor и прочие поля подробно определены в [полном справочнике]({{ '/reference/' | relative_url }}) и [границах доверия MCP]({{ '/contracts/mcp-mutation-trust-boundaries/' | relative_url }}).

## Миграция

По умолчанию `okf migrate` показывает план. Запись требует явных входных данных и разрешения. Миграция не выдумывает автора, источники, проверки, состояние или свежесть. Для старых цитат нужны явные сопоставления; их JSON-схема и правила точного совпадения находятся в [руководстве]({{ '/ru/migration/' | relative_url }}).

Входные данные проверяются до определения исходного формата. Отсутствующий документ блокирует миграцию с `migration_document_missing`. Предпросмотр, отказ и другие пути без публикации сохраняют весь набор файлов и байтов, без временных артефактов `.okf`. При действительной публикации корневой `index.md` записывается последним.

Применение перехода v0.1 → v0.2 требует proof `format_version: 2`, непустого `resolution_digest`, `expected_plan_digest` и того же `expected_source`. Авторитетная ревизия находится в `proof.base_revision`; отдельного поля `expected_revision` для миграции нет. Повтор того же применения воспроизводит записанный результат без второй публикации.

Для уже достигнутого формата поведение отличается: MCP не открывает хранилище и не требует proof; CLI без записи строит proof без открытия хранилища; CLI с `--write` проводит пустую транзакцию и сохраняет её квитанцию в `.okf`. Файлы самого набора знаний остаются прежними. Полные правила возвратов, повторов и отказов сохранены в [справочнике]({{ '/reference/' | relative_url }}).

## Вычисления и дополнительные связи

`computation`, `executor.resource` и `attester.resource` — данные; toolkit не запускает их по факту присутствия в документе. Нужны отдельно выбранная доверенная среда и разрешение. Спецификация допускает передачу значений объявленных параметров агентом, но запрещает ему создавать или изменять санкционированное вычисление. Квитанция `store.CommitReceipt` не связана с `executor.receipt`.

YAML `relations` — расширение этого проекта, а не часть исходного OKF v0.2. Стандартный способ навигации между заметками — Markdown-ссылки. Профиль графа не выбирает версию документа.

## Разработка

```sh
go test ./...
go vet ./...
git diff --check
```

При изменении скилов выполните `node scripts/update-skills-lock.mjs --check` и `node scripts/check-skill-package.mjs`; зависимости и регистрация описаны в [английском справочнике]({{ '/reference/' | relative_url }}). Проверка файлов пакета не доказывает активацию скила или вызов инструментов в настоящем клиенте.
