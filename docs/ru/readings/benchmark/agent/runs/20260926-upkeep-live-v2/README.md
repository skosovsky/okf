# Задача 013: автор → читатель с включённой/выключенной проверкой, v2
{: #section-1}

Этот заранее зарегистрированный повторный запуск завершился с `valid: true`. Сохранены [план](https://github.com/skosovsky/okf/blob/61e75e9aa9a8719dfb480bf1f5226553b3a21d70/benchmark/agent/runs/20260926-upkeep-live-v2/plan.json), [исходные записи](https://github.com/skosovsky/okf/blob/61e75e9aa9a8719dfb480bf1f5226553b3a21d70/benchmark/agent/runs/20260926-upkeep-live-v2/rows.json), [аудит](https://github.com/skosovsky/okf/blob/61e75e9aa9a8719dfb480bf1f5226553b3a21d70/benchmark/agent/runs/20260926-upkeep-live-v2/audit.json), [метка завершения](https://github.com/skosovsky/okf/blob/61e75e9aa9a8719dfb480bf1f5226553b3a21d70/benchmark/agent/runs/20260926-upkeep-live-v2/audit.json.complete) и [отчёт](https://github.com/skosovsky/okf/blob/61e75e9aa9a8719dfb480bf1f5226553b3a21d70/benchmark/agent/runs/20260926-upkeep-live-v2/report.json). Тот же закоммиченный анализатор воспроизводит `report.json` байт в байт. Хеши записей и аудита в метке завершения совпадают с сохранёнными файлами. V2 оценён по [зафиксированному протоколу]({{ '/ru/readings/benchmark/agent/upkeeplive/LIVE-V2/' | relative_url }}); предыдущий [запуск v1]({{ '/ru/readings/benchmark/agent/runs/20260926-upkeep-live-v1/README/' | relative_url }}) остаётся некорректным по исходному контракту оценивания.

| Заранее зарегистрированный результат | Проверка выключена | Проверка включена |
| --- | ---: | ---: |
| Документ заметки обновлён | 2/2 | 1/2 |
| Независимый читатель ответил правильно по строгому оценщику | 0/2 | 1/2 |
| Неправильный ответ | 1/2 | 1/2 |
| Ответ не поддаётся оценке из-за неподдерживаемой ссылки | 1/2 | 0/2 |
| Операционный сбой | 0/2 | 0/2 |

Эти строгие оценки требуют пояснений по случаям. В `upkeep-reversal` при выключенной проверке `decision.md` обновили до режима B, и читатель ответил `Mode B`, тогда как зарегистрированный точный ответ — `B`; поэтому оценщик признал его **неправильным**, несмотря на совпадающий смысл. При включённой проверке документ остался с режимом A после изменения кода на B, и читатель ответил `Mode A`. После правки проверка по-прежнему возвращала `needs_review`. В `upkeep-truncated` оба документа объясняют, что по частично сохранённым данным нельзя установить состояние развёртывания, и оба читателя ответили `Insufficient evidence.` («недостаточно данных»). При включённой проверке читатель сослался на допустимый идентификатор артефакта `handler` и получил правильную оценку. При выключённой проверке он сослался на текстовое описание, отсутствующее среди идентификаторов артефактов набора, поэтому содержательно уместный ответ признан **не поддающимся оценке** по заранее зарегистрированным правилам ссылок. Итоговое состояние `reviewed_updated` при включённой проверке фиксирует изменение файла заметки, а не независимое доказательство правильности его содержания.

Аудит фиксирует все четыре ожидаемые пары автора/читателя, 10 вызовов модели, 155,387 наблюдаемых входных и выходных токенов, ноль вызовов с неизвестным потреблением, 10 разных идентификаторов сессий модели и успешную проверку Go CLI каждого итогового набора. SHA-256 плана — `98f16ab46d4241bf6a8cfb8dcd7f3ff45189021dee362d5c0fc65073b38adc7f`; записей — `086005a2e123b126c2804d9d9b28b26241c97c9abea60b15bf24bf1d6f938707`; аудита — `23ec5bcb8fc29f4a987da1b09958f66be0aa8dfc9350483da56e559ed3485eb9`. Стоимость в USD недоступна.

Это описательный результат по двум случаям. Группа с включённой проверкой объединяет напоминание о пересмотре, реальную обратную связь проверки и дополнительную правку автора, поэтому эксперимент не выделяет эффект самой проверки. Строгие оценки читателей 0/2 против 1/2 также занижают смысловое качество ответов при выключённой проверке из-за требований к точному ответу и формату ссылки. Эти наблюдения дают регрессионные случаи и основания для более ясного контракта оценки, а не для утверждения, что включённая проверка улучшает качество ответов читателя.
