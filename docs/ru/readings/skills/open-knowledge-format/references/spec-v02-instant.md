# Open Knowledge Format (OKF) {#open-knowledge-format-okf}

**Версия 0.2**

OKF — открытый формат, удобный для людей и агентов. Он описывает *знания*: метаданные, контекст и отобранные полезные сведения о данных и системах. Формат рассчитан на документы, которые люди пишут, агенты создают, организации передают друг другу, а люди и агенты читают.

Формат намеренно прост: каталог файлов Markdown с блоками метаданных YAML в начале каждого файла. Нет реестра схем, центрального управляющего органа или обязательных инструментов. Если вы можете выполнить `cat` для файла, вы можете прочитать OKF; если можете выполнить `git clone` для репозитория, можете передать его другим.

Документ самодостаточен: он определяет всё необходимое для создания и чтения OKF v0.2. Изменения относительно v0.1 перечислены в §13.

<a id="1-motivation"></a>

## 1. Мотивация {#section-1-motivation}

Способы представления знаний для AI-агентов быстро развиваются, и появляются многочисленные несовместимые соглашения. OKF исходит из того, что знания лучше представлять в общедоступных, устоявшихся форматах, которые:

- **Читаемы** человеком без специальных инструментов.
- **Разбираемы** агентами без специальных SDK.
- **Позволяют сравнивать изменения** в системе контроля версий.
- **Переносимы** между инструментами и организациями и сохраняют доступность со временем.

Всё чаще корпус знаний создаётся не один раз для последующего чтения: агенты **непрерывно пишут и поддерживают его**. Когда большинство понятий создают машины, читателю нужны ответы на вопросы, которые обычное соглашение «Markdown с метаданными» явно не выделяет:

1. Из чего это создано и как проверено? (**Происхождение**.)
2. Насколько этому можно доверять? (**Доверие**.)
3. Верно ли это до сих пор? (**Актуальность**.)
4. Это текущая версия? (**Жизненный цикл**.)
5. Получено ли это число предписанным способом? (**Аттестация вычисления**.)

OKF v0.2 явно описывает происхождение, доверие, жизненный цикл и аттестацию, сохраняя минимум предписаний. Формат задаёт минимум правил. Он стандартизирует только небольшой набор структурных соглашений, нужных для самоописания корпуса знаний; остальные решения остаются за создателем.

### Цели {#goals}

1. Определить универсальный формат, в который **создатели** — люди, агенты и процессы экспорта — могут записывать знания.
2. Объяснить, как **читатели** — агенты, интерфейсы, поисковые индексы и детерминированный код — должны читать документы и переходить между ними.
3. Облегчить **обмен** знаниями между системами и организациями.
4. Стандартизировать небольшой набор полей метаданных, который позволяет **оценивать доверие** к корпусу, поддерживаемому агентами, без требования конкретной среды исполнения.

### Что не входит в цели {#non-goals}

- Задание фиксированной классификации типов понятий.
- Предписание инфраструктуры хранения, предоставления данных или запросов.
- Замена специализированных схем: Avro, Protobuf, OpenAPI и других. OKF *ссылается* на них, а не включает их в себя.
- Определение стандарта упаковки или вызова кода, на который ссылается исполнитель или проверяющий. OKF фиксирует интерфейс, а не способ упаковки.

<a id="2-terminology"></a>

## 2. Термины {#section-2-terminology}

- **Набор знаний** (Knowledge Bundle, далее **набор**): самодостаточная иерархическая коллекция документов со знаниями; единица распространения.
- **Понятие** (Concept): единица знаний внутри набора, представленная одним документом Markdown. Может описывать конкретный объект — таблицу или API, — абстрактную идею — метрику или бизнес-процесс, — либо что-то между ними.
- **Идентификатор понятия** (Concept ID): путь к файлу понятия внутри набора без суффикса `.md`.
- **Начальный блок метаданных** (Frontmatter): блок YAML в начале файла Markdown, ограниченный строками `---`.
- **Тело документа** (Body): всё содержимое файла после начального блока метаданных.
- **Ссылка** (Link): стандартная ссылка Markdown от одного понятия к другому, выражающая связь сверх неявной иерархии родителей и потомков.
- **Источник** (Source): материал внутри или вне набора, из которого получено понятие; записывается в поле `sources`.
- **Происхождение** (Provenance): совокупность источников, из которых получено понятие.
- **Признак надёжности источника** (Credibility signal): объективный факт об отдельном источнике (`author`, `usage_count`, `last_modified`), используемый для оценки доверия. OKF записывает признаки, а не итоговый вывод (§5.1).
- **Участник действия** (Actor): строка, обозначающая того, кто выполнил действие. Для агентов используется `<producer>/<version>`, для людей — `human:<id>`, для автоматических процессов — `process:<id>` (§7).
- **Уровень доверия** (Trust tier): уровень, выводимый из поля `verified`: не проверено, подтверждено машиной или проверено человеком (§5.3).
- **Аттестуемое вычисление** (Attested Computation): понятие (`type: Attested Computation`), описывающее утверждённый способ вычисления значения, чтобы читатель мог подтвердить, что значение получено именно его выполнением (§10).
- **Исполнитель** (Executor): инструкции запуска или код, который выполняет вычисление и возвращает свидетельство выполнения (§10.2).
- **Свидетельство выполнения** (Receipt): подтверждающие данные, возвращаемые запуском; их состав задаёт `executor.receipt`. Это результат работы во время исполнения, который не хранится в наборе (§10).
- **Проверяющий вычисление** (Attester): детерминированный код без LLM, который анализирует свидетельство выполнения и возвращает вердикт (§10.2).

<a id="3-bundle-structure"></a>

## 3. Структура набора {#section-3-bundle-structure}

Набор — дерево каталогов с файлами Markdown. Структура каталогов не зависит от предметной области: создатели организуют понятия так, как удобно для описываемых знаний.

```
path/to/bundle/
  index.md                      # Необязательно. Список содержимого для постепенного знакомства.
  log.md                        # Необязательно. Хронологическая история обновлений.
  <concept>.md                  # Понятие в корне набора.
  <subdirectory>/               # Подкаталоги объединяют понятия в группы.
    index.md
    <concept>.md
    <subdirectory>/
      ...
```

Набор МОЖЕТ распространяться как:

- Репозиторий Git: рекомендуемый вариант, поскольку он предоставляет историю, сведения об авторах и сравнение изменений.
- Архив tar или zip с содержимым каталога.
- Подкаталог более крупного репозитория.

<a id="31-reserved-filenames"></a>

### 3.1 Зарезервированные имена файлов {#section-31-reserved-filenames}

Следующие имена имеют заданное значение на любом уровне иерархии и НЕ ДОЛЖНЫ использоваться для документов понятий:

| Имя файла | Назначение |
|-----------|------------|
| `index.md` | Список содержимого каталога. См. §8. |
| `log.md` | История обновлений. См. §9. |

Все остальные файлы `.md` — документы понятий.

Теги явно представлены полем метаданных `tags` (§4.1). OKF не задаёт отдельного формата файла для объединения документов по тегу. Если читателю нужен просмотр по тегам, он может построить его при чтении, просканировав метаданные.

<a id="4-concept-documents"></a>

## 4. Документы понятий {#section-4-concept-documents}

Каждое понятие — файл Markdown в кодировке UTF-8, состоящий из двух частей:

1. **Начальный блок метаданных YAML**, начинающийся строкой `---` в начале файла и заканчивающийся отдельной строкой `---`.
2. **Тело Markdown** с содержимым произвольной формы.

<a id="41-frontmatter"></a>

### 4.1 Начальный блок метаданных {#section-41-frontmatter}

```yaml
---
type: <Имя типа>                  # ОБЯЗАТЕЛЬНО
title: <Необязательное отображаемое имя>
description: <Необязательное краткое описание в одну строку>
resource: <Необязательный канонический URI описываемого объекта>
tags: [<тег>, <тег>, ...]          # Необязательно
# ... поля происхождения, доверия, жизненного цикла и вычислений (см. §5, §10)
# ... другие пары ключ/значение, определённые создателем
---
```

**Обязательные поля:**

- `type`: короткая строка, определяющая вид понятия. Читатели используют её для маршрутизации, фильтрации и отображения. Примеры значений: `BigQuery Table`, `BigQuery Dataset`, `API Endpoint`, `Metric`, `Playbook`, `Reference`, `Attested Computation`.

  Значения типов **не регистрируются централизованно**. Создателям СЛЕДУЕТ выбирать описательные и понятные значения; читатели ДОЛЖНЫ корректно обрабатывать неизвестные типы, обычно представляя их как обычные понятия.

`type` — единственный ключ, обязательный всегда; понятие только с полем `type` полностью соответствует формату (§11).

**Рекомендуемые поля:**

- `title`: понятное человеку отображаемое имя. Если оно отсутствует, читатели МОГУТ вывести его из имени файла.
- `description`: одно предложение, описывающее понятие. Используется генераторами `index.md`, в поисковых фрагментах и предварительном просмотре.
- `resource`: URI, однозначно определяющий объект, который описывает понятие. Отсутствует у понятий, описывающих абстрактные идеи вместо конкретных ресурсов.
- `tags`: список коротких строк YAML для группировки по признакам, пересекающим основную иерархию.

Также могут присутствовать необязательные группы полей **происхождения**, **доверия** и **жизненного цикла** (§5), а у понятий типа Attested Computation — поля **вычисления** (§10).

**Расширения:** создатели МОГУТ добавлять любые ключи. Читателям СЛЕДУЕТ сохранять неизвестные ключи при чтении с последующей записью и они НЕ ДОЛЖНЫ отвергать документы с неизвестными полями.

<a id="42-body"></a>

### 4.2 Тело документа {#section-42-body}

Тело — стандартный Markdown. Создателям СЛЕДУЕТ предпочитать структурированный Markdown — заголовки, списки, таблицы и блоки кода с ограждением — свободной прозе, поскольку структура облегчает и чтение человеком, и поиск агентами.

Обязательных разделов тела нет. Следующие заголовки имеют **общепринятое** значение, и их СЛЕДУЕТ использовать, когда это уместно:

| Заголовок | Назначение |
|-----------|------------|
| `# Schema` | Структурированное описание столбцов или полей объекта. |
| `# Examples` | Конкретные примеры использования, часто в блоках кода с ограждением. |
| `# Computation` | Утверждённое вычисление понятия Attested Computation. См. §10. |

Для ссылки на внешний источник отдельного утверждения используются сноски Markdown, связанные с записями `sources`, а не список цитат в теле (§5.1).

<a id="43-example-a-concept-bound-to-a-resource"></a>

### 4.3 Пример: понятие, связанное с ресурсом {#section-43-example-a-concept-bound-to-a-resource}

```markdown
---
type: BigQuery Table

description: Одна строка на каждый завершённый заказ клиента по всем каналам.

| Столбец       | Тип       | Описание |
|---------------|-----------|----------|

# Соединения

Соединяется с [таблицей клиентов](/tables/customers.md) по `customer_id`.
```

<a id="5-provenance-trust-and-lifecycle"></a>

## 5. Происхождение, доверие и жизненный цикл {#section-5-provenance-trust-and-lifecycle}

Эти группы полей позволяют ответить на вопросы «откуда это взялось», «насколько этому доверять» и «актуально ли это» по метаданным. Все они необязательны. Их отсутствие имеет значение: непроверенное понятие отличается от проверенного, но никогда не отвергается (§11).

Каждый ключ OKF со значением времени содержит дату и время ISO 8601 с явно заданным смещением UTC, например `2026-06-30T14:00:00Z`.

<a id="51-provenance-sources"></a>

### 5.1 Происхождение: `sources` {#section-51-provenance-sources}

`sources` перечисляет материалы внутри или вне набора, из которых получено понятие.

```yaml
sources:
  - id: ga4-schema
    resource: https://developers.google.com/analytics/bigquery/export-schema
    title: Схема экспорта GA4 в BigQuery
    author: team:ga4-docs
    usage_count: 5000
    last_modified: 2026-05-30T00:00:00Z
usage_window: { from: 2026-06-01T00:00:00Z, to: 2026-06-30T00:00:00Z }
```

Каждая запись `sources` содержит:

- `resource`: ОБЯЗАТЕЛЬНО внутри записи. Обозначает либо конкретный материал, который читатель может открыть — абсолютный URL, путь относительно набора или путь в подкаталог `references/` (§6), — либо описание совокупности или области, которое нельзя открыть, например `all queries in BigQuery project X` («все запросы в проекте BigQuery X»).
- `id`: необязательно. Стабильный ключ для привязки отдельных утверждений к источнику; см. ниже. Его СЛЕДУЕТ указывать, когда тело ссылается на источник.
- `title`: необязательно. Понятная человеку подпись источника.
- Необязательные признаки надёжности `author`, `usage_count` и `last_modified`, описанные далее.

**Признаки надёжности источника.** OKF записывает объективные признаки каждого источника, чтобы читатель мог оценивать доверие к понятию по источникам, из которых оно получено. Оценка надёжности не хранится: она субъективна, не переносится между читателями и устаревает. Надёжность *выводится* из признаков, как и уровни доверия (§5.3), а не хранится. Каждый признак необязателен и записывается в запись `sources`:

- `author`: кто или что создало источник; используется соглашение об участниках действия (§7). Признак авторитетности.
- `usage_count`: число использований `resource` — просмотров панели, выполнений запросов, чтений страницы — за `usage_window`. Признак востребованности и действующего использования. Для отдельного материала это число использований самого материала; для описания области — число использований внутри этой области, затрагивающих понятие.
- `last_modified`: когда изменился сам источник. Признак давности, отличный от `generated.at` (§5.2), который фиксирует время написания понятия.
- `usage_window`: записывается один раз рядом с `sources` и задаёт диапазон дат и времени `{ from, to }` для всех `usage_count`. Отдельная запись МОЖЕТ задать собственный `usage_window`, переопределив общий.

`usage_count` — приблизительный признак. Его можно сравнивать на уровне «используется или не используется», порядка величины и с историей самого источника, но нельзя использовать как точный рейтинг между разными видами источников: выполнения запроса по расписанию и намеренные просмотры панели человеком имеют разный вес. Читателям СЛЕДУЕТ воспринимать это поле как признак использования и тенденции, а не итоговую оценку.

Цепочка происхождения выражается ссылками, а не отдельным полем. Когда `resource` указывает на другое понятие OKF, связь происхождения уже присутствует в графе набора (§6), поэтому читатель МОЖЕТ рекурсивно изучать `sources` источника и распространять оценку надёжности по цепочке. Внешние конечные источники несут только собственные признаки. Более глубокая цепочка происхождения — явное внешнее `derived_from` или происхождение данных — выходит за рамки v0.2.

**Привязка отдельного утверждения к источнику.** Для конкретного утверждения используйте сноску Markdown, метка которой совпадает с `sources[].id`:

```markdown
Таблица `events_` разбивается по дням на `events_YYYYMMDD`.[^ga4-schema]

[^ga4-schema]: Схема экспорта GA4 в BigQuery
```

Метка сноски — ключ связи с `sources`. Читатели определяют источник по соответствующей записи, а не разбирают текст сноски. Метки задаются ключами, а не позициями (`sources[0]`), поскольку агенты постоянно переписывают документы: при перестановке списка позиционный индекс незаметно связывает утверждение с неверным источником, а стабильный `id` сохраняет связь.

<a id="52-trust-generated-and-verified"></a>

### 5.2 Доверие: `generated` и `verified` {#section-52-trust-generated-and-verified}

`generated` описывает, как создано текущее содержимое. `verified` записывает, кто или что подтвердило содержимое относительно его источников или `resource`. Поля разделены, поскольку тот, кто *написал* понятие, не обязательно является тем, кто его *подтвердил*.

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
```

- `generated.by`: ОБЯЗАТЕЛЬНО внутри `generated`. Участник действия (§7).
- `generated.at`: дата и время ISO 8601 последнего существенного изменения содержимого. Читатели используют её, чтобы отличать недавнюю правку от устаревшего факта.

```yaml
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

- `verified`: список событий проверки, каждое с `by` — участником действия — и `at` — датой и временем ISO 8601. Несколько записей описывают независимые проверки, например согласование человеком и ночную проверку процессом. Давность проверки определяется последним `at`.
- `verified` не зависит от `generated.at`: содержимое может измениться без повторного подтверждения, а факты могут быть подтверждены повторно без нового создания.
- Единственный проверяющий МОЖЕТ быть записан одной структурой `{ by, at }` без маркера списка. Читатели ДОЛЖНЫ воспринимать такую структуру как список из одного элемента:

```yaml
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
```

<a id="53-trust-tiers"></a>

### 5.3 Уровни доверия {#section-53-trust-tiers}

Читатели выводят уровень доверия из `verified`, от низшего к высшему:

- Нет ключа `verified` ⇒ **не проверено** (unverified).
- `verified` содержит только участников без префикса `human:` ⇒ **подтверждено машиной** (machine-confirmed).
- `verified` содержит участника `human:<id>` ⇒ **проверено человеком** (human-reviewed).

Понятие без метаданных доверия по-прежнему можно читать; читатели НЕ ДОЛЖНЫ его отвергать (§11). Уровни доверия — рекомендательные признаки, а не управление доступом.

<a id="54-lifecycle-status"></a>

### 5.4 Жизненный цикл: `status` {#section-54-lifecycle-status}

```yaml
status: stable        # draft | stable | deprecated
```

- `draft`: ещё не проверено; возможно, неполное.
- `stable`: значение по умолчанию; готово к использованию.
- `deprecated`: сохраняется ради ссылок и истории; больше не актуально.

Отсутствующий `status` ⇒ `stable`.

<a id="55-lifecycle-stale_after"></a>

### 5.5 Жизненный цикл: `stale_after` {#section-55-lifecycle-stale_after}

```yaml
stale_after: 2026-09-23T00:00:00Z   # содержимое устаревает в этот момент или позднее
```

Необязательное поле. Абсолютный момент времени. Понятие считается устаревшим при `now >= stale_after`. Абсолютный момент, в отличие от относительного TTL, позволяет принимать решение об устаревании простым сравнением без обращения ко времени чтения понятия.

<a id="6-cross-linking-and-paths"></a>

## 6. Связи и пути {#section-6-cross-linking-and-paths}

<a id="61-links-between-concepts"></a>

### 6.1 Ссылки между понятиями {#section-61-links-between-concepts}

Понятия МОГУТ ссылаться друг на друга стандартными ссылками Markdown. Поддерживаются две формы:

- **Абсолютная относительно набора:** начинается с `/` и отсчитывается от корня набора. Это **рекомендуемая** форма: она сохраняет работоспособность при перемещении документов внутри их подкаталога.

  ```markdown
  Ключ соединения указан в [таблице клиентов](/tables/customers.md).
  ```

- **Относительная:** обычный относительный путь Markdown.

  ```markdown
  См. [соседнее понятие](./other.md).
  ```

Ссылка от понятия A к понятию B утверждает наличие *связи*. Её конкретный вид — родитель/потомок, ссылка на источник, соединение или зависимость — задаётся окружающим текстом, а не самой ссылкой. Читатели, строящие граф, обычно считают все ссылки направленными рёбрами связи без типа.

Читатели ДОЛЖНЫ допускать неработающие ссылки: ссылка на отсутствующую цель в наборе не является некорректной; она может обозначать ещё не записанное знание.

<a id="62-path-valued-fields"></a>

### 6.2 Поля со значением пути {#section-62-path-valued-fields}

Несколько полей содержат путь или URI: `resource`, `sources[].resource`, `computation`, `executor.resource` и `attester.resource` (§10). Вместо пути `sources[].resource` может содержать описание области (§5.1). Каждое поле со значением пути принимает:

- Абсолютный URL, например `https://...`.
- Путь относительно набора, начинающийся с `/`.
- Относительный путь, например `../computations/revenue.md`.

<a id="63-the-references-convention"></a>

### 6.3 Соглашение о `references/` {#section-63-the-references-convention}

Подкаталог `references/` по соглашению содержит копии внешних материалов, инструкции запуска или код как полноценные понятия внутри набора. Источники, исполнители и проверяющие часто ссылаются на него, например на `references/attesters/revenue.py`. Это соглашение об именовании, а не требование.

---

<a id="7-actor-convention"></a>

## 7. Соглашение об участниках действия {#section-7-actor-convention}

Поля, записывающие личность или идентичность (`generated.by`, `verified[].by`), используют единое соглашение:

- `<producer>/<version>` для агентов и инструментов, например `reference_agent/gemini-2.5-pro`.
- `human:<id>` для человека, например `human:ahormati`.
- `process:<id>` для автоматического процесса, например `process:finance-nightly`.

Читатели, определяющие уровень доверия (§5.3), используют префикс `human:`, поэтому создатели ДОЛЖНЫ применять его для содержимого, написанного или подтверждённого человеком.

<a id="8-index-files"></a>

## 8. Файлы оглавления {#section-8-index-files}

Файл `index.md` МОЖЕТ находиться в любом каталоге, включая корень набора. Он перечисляет содержимое каталога и позволяет **постепенно знакомиться с набором**: человек или агент видит доступные материалы перед открытием отдельных документов.

Файлы оглавления не содержат начального блока метаданных, кроме одного исключения: `index.md` в корне набора МОЖЕТ содержать ключ `okf_version` (§12). Тело состоит из одного или нескольких разделов, каждый из которых объединяет понятия под заголовком:

```markdown
# Заголовок раздела / группы

* [Название 1](relative-url-1) - краткое описание элемента 1
* [Название 2](relative-url-2) - краткое описание элемента 2

# Другой раздел

* [Подкаталог](subdir/) - краткое описание подкаталога
```

Записям СЛЕДУЕТ включать описание из метаданных понятия, на которое они ссылаются. Создатели МОГУТ автоматически формировать `index.md`; читатели МОГУТ создавать его при чтении, когда он отсутствует.

<a id="9-log-files"></a>

## 9. Файлы журнала {#section-9-log-files}

Файл `log.md` МОЖЕТ находиться на любом уровне иерархии и хранить историю изменений соответствующей области. Формат — плоский список записей, сгруппированных по датам, сначала новые:

```markdown
# Журнал обновлений каталога

## 2026-05-22
* **Обновление**: Добавлено описание таблицы BigQuery [Метрики клиентов](/tables/customer-metrics.md).
* **Создание**: Подготовлена [инструкция Dataplex](/playbooks/dataplex.md).

## 2026-05-15
* **Инициализация**: Создана базовая структура каталогов.
```

Заголовки дат ДОЛЖНЫ иметь форму ISO 8601 `YYYY-MM-DD`. Записи журнала — проза; первое выделенное жирным слово (`**Update**`, `**Creation**`, `**Deprecation**` — «обновление», «создание», «вывод из использования») — соглашение, а не требование.

<a id="10-attested-computations-concept"></a>

## 10. Понятие аттестуемого вычисления {#section-10-attested-computations-concept}

Понятие Attested Computation описывает не только то, что *означает* значение, но и утверждённый способ его *вычисления*. Это позволяет читателю подтвердить, что агент выполнил утверждённое вычисление, а не придумал своё. Происхождение (§5.1) отвечает на вопрос «откуда взялось это утверждение»; аттестация — «получено ли это число предписанным способом». OKF записывает вычисление и средства его проверки; сам формат ничего не выполняет.

<a id="101-a-computation-is-its-own-concept"></a>

### 10.1 Вычисление — самостоятельное понятие {#section-101-a-computation-is-its-own-concept}

Утверждённое вычисление — отдельное понятие с `type: Attested Computation`. Понятие, которому нужно значение, например `Metric` или `BigQuery Table`, ссылается на него обычной ссылкой Markdown (§6). Отдельное понятие нужно по трём причинам:

- **`runtime` определяет смысл `parameters`.** В зависимости от среды исполнения параметр означает переменную привязки SQL, переменную dbt или аргумент Python. Когда `runtime` и `parameters` находятся в одном блоке метаданных, правила привязки понятны из самого блока.
- **Одно вычисление, много читателей.** Одно вычисление может использоваться метрикой, понятием панели и отчётом. Как понятие оно определяется один раз и используется повторно по ссылке.
- **Состояние доверия относится к одному вычислению.** `verified`, `stale_after` и единственный `attester` описывают один объект. Выручка, прибыль и маржа проверяются и аттестуются независимо: это три понятия, а не три записи в одном блоке метаданных.

<a id="102-contract-fields"></a>

### 10.2 Поля контракта {#section-102-contract-fields}

Контракт задаётся полями верхнего уровня в начальном блоке метаданных понятия. Помимо происхождения, доверия и жизненного цикла (§5), понятие Attested Computation содержит:

- `runtime`: ОБЯЗАТЕЛЬНО для этого типа. Единственное поле, указывающее способ запуска вычисления; тем самым оно определяет, как исполнитель и проверяющий интерпретируют вычисление и что означают `parameters`. Примеры: `bigquery`, `postgres`, `dbt`, `python`, `Looker`.
- `parameters`: список именованных параметров с типами, значения которых агент может задать. Каждая запись: `{ name, type, required }`. Правила привязки определяются `runtime`.
- `computation`: необязательно. Путь (§6.2) к файлу с вычислением вместо встроенного блока кода (§10.3). При отсутствии вычислением служит блок кода в разделе `# Computation` тела документа.
- `executor`: способ запуска вычисления. `resource` указывает на инструкции или код; запускающий — агент либо детерминированный код читателя — следует им. `receipt` объявляет поля, которые должен вернуть запуск: свидетельство для проверяющего, например BigQuery `job_id` и SQL, который действительно выполнило задание.
- `attester`: детерминированная проверка. `resource` указывает на код без LLM, который принимает свидетельство выполнения и возвращает вердикт. Предполагается запуск на стороне читателя.

Что именно стоит за `resource` — навык (Skill), скрипт или контейнер — вопрос упаковки. OKF фиксирует интерфейс, а не упаковку (§1).

```markdown
---
type: Attested Computation
title: Выручка за финансовый год
description: Признанная выручка за финансовый год по определению финансового отдела.
status: stable
runtime: bigquery
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/skills/run-on-bq.md
  receipt: [job_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23T00:00:00Z
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Политика признания выручки
---

# Computation

    SELECT SUM(amount) AS revenue
    FROM finance.recognized_revenue
    WHERE fiscal_year = @year

Вычисление связывает только объявленные `parameters` согласно политике признания.[^rev-policy]

[^rev-policy]: Политика признания выручки
```

<a id="103-the-computation"></a>

### 10.3 Вычисление {#section-103-the-computation}

Задайте вычисление одним из двух способов:

- **В документе:** единственный блок кода с ограждением в теле под `# Computation`. Подходит для короткого вычисления, проверяемого вместе с контрактом.
- **В файле:** задайте для `computation` путь (§6.2) и не добавляйте блок кода в тело. Подходит для длинного или сгенерированного вычисления либо вычисления, уже хранящегося в отдельном файле, который используется инструментами вне OKF.

```yaml
runtime: bigquery
computation: references/computations/lib/revenue.sql
parameters:
  - { name: year, type: integer, required: true }
```

Агент МОЖЕТ задавать только *значения* объявленных `parameters`; он НЕ ДОЛЖЕН писать или редактировать вычисление. Читатель отвечает за привязку значений параметров к `computation` и формирование исполняемого результата. Проверяющий независимо повторяет ту же привязку и сравнивает её с тем, что действительно выполнялось. Поскольку сравнивается развёрнутый, скомпилированный результат из свидетельства (`executed_sql`, `compiled_sql`), переписанный запрос, подменённый файл вычисления или изменённая зависимость не проходят проверку. Типизированный интерфейс, позволяющий задавать только параметры, превращает вопрос «выполнялось ли утверждённое вычисление» в механическое сравнение вместо субъективного суждения.

<a id="104-concepts-that-use-a-computation"></a>

### 10.4 Понятия, использующие вычисление {#section-104-concepts-that-use-a-computation}

Документ редко описывает только одно вычисление. Обзор отчёта о финансовых результатах, рассматривающий выручку, прибыль и маржу, остаётся одним читаемым понятием и ссылается на отдельное Attested Computation для каждого показателя:

```markdown
---
type: Metric
title: Выручка
description: Признанная выручка за финансовый год.
tags: [finance, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
---

# Определение

Признанная выручка — сумма `amount` по строкам, учтённым за финансовый год;
её рассчитывает [вычисление выручки](../computations/revenue.md).
```

Поскольку каждое вычисление — отдельное понятие, выручка может оставаться актуальной, когда прибыль уже прошла `stale_after`; каждое аттестуется по собственному запуску. Совместное размещение определяется каталогами — например, папкой `computations/` с `index.md`, — а не метаданными.

<a id="105-how-a-consumer-uses-it-informative"></a>

### 10.5 Использование читателем (информационный раздел) {#section-105-how-a-consumer-uses-it-informative}

Этот подраздел информационный, а не нормативный. Описанные ниже результаты исполнения **не** хранятся в наборе.

1. **Обнаружение** через `type: Attested Computation`: признак в метаданных можно включить в `index.md`. Читатель открывает понятие непосредственно или переходит по ссылке из понятия, которое его использует.
2. **Загрузка** контракта из метаданных и вычисления из тела либо файла, названного в `computation`.
3. **Параметризация:** агент задаёт значения объявленных параметров.
4. **Выполнение:** исполнитель запускает вычисление с привязанными значениями и возвращает свидетельство в форме `executor.receipt`.
5. **Аттестация:** читатель запускает проверяющего для свидетельства. Проверка подтверждает происхождение — выполненное вычисление совпадает с `computation`, привязанным к заявленным параметрам, а не с SQL, написанным агентом, — и точность — отображаемое значение совпадает с авторитетным источником из свидетельства, повторно прочитанным по идентификатору задания, а не взятым из текста агента.
6. **Допуск результата:** отказ от отображения при неуспешной аттестации; предупреждение или отказ при `now >= stale_after`. При успехе показать вердикт, например ссылку на журнал задания, чтобы основания доверия были видны.

<a id="106-verification-versus-attestation"></a>

### 10.6 Проверка определения и аттестация запуска {#section-106-verification-versus-attestation}

`verified` (§5.2) и аттестация различаются; нужны обе:

- `verified` подтверждает, что *определение* по-прежнему соответствует политике. Проверка относится к документу, требует времени и записывается в наборе.
- Аттестация подтверждает, что отдельный *запуск* получил значение утверждённым способом. Она относится к каждому вызову, проводится во время исполнения и не хранится в наборе.

Понятие с устаревшим определением всё ещё может успешно пройти аттестацию, а недавно проверенное определение по-прежнему требует аттестации каждого запуска. Поэтому нужны обе проверки.

<a id="11-conformance"></a>

## 11. Соответствие формату {#section-11-conformance}

Набор **соответствует** OKF v0.2, если:

1. Каждый файл `.md` без зарезервированного имени в дереве содержит начальный блок метаданных YAML, который можно разобрать.
2. Каждый блок метаданных содержит непустое поле `type`.
3. Каждый присутствующий файл с зарезервированным именем (`index.md`, `log.md`) следует структуре §8 и §9 соответственно.

При наличии групп полей доверия, жизненного цикла, происхождения или вычисления создателям СЛЕДУЕТ следовать §5–§10, а читатели:

- ДОЛЖНЫ воспринимать одиночную структуру `verified` как список из одного элемента (§5.2).
- НЕ ДОЛЖНЫ отвергать понятие из-за отсутствия любой необязательной группы полей (§5.3).
- СЛЕДУЕТ выводить уровни доверия и устаревание только из определённых здесь полей и СЛЕДУЕТ показывать неуспешную аттестацию, а не молча отбрасывать её (§10.5).

Читателям СЛЕДУЕТ считать все остальные ограничения мягкими рекомендациями. В частности, читатели НЕ ДОЛЖНЫ отвергать набор из-за:

- Отсутствия необязательных полей метаданных.
- Неизвестных значений `type`.
- Неизвестных дополнительных ключей метаданных.
- Неработающих ссылок между понятиями.
- Отсутствия файлов `index.md`.

<a id="12-versioning"></a>

## 12. Версионирование {#section-12-versioning}

Этот документ определяет OKF версии **0.2**. Версии имеют вид `<major>.<minor>`:

- Увеличение **минорной** версии добавляет обратно совместимые возможности: новые необязательные поля или новые общепринятые заголовки разделов.
- Увеличение **мажорной** версии может вводить несовместимые изменения: переименование обязательных полей или изменение зарезервированных имён файлов.

Наборы МОГУТ объявлять поддерживаемую версию через `okf_version: "0.2"` в начальном блоке метаданных корневого `index.md` — единственном месте, где в `index.md` допускаются метаданные. Читателям, не понимающим заявленную версию, СЛЕДУЕТ попытаться прочитать набор в меру своих возможностей вместо отказа.

### Рассмотрено и отложено {#considered-and-deferred}

Следующие вопросы намеренно оставлены будущей редакции:

- Полный протокол исполнения: форматы передачи свидетельства и вердикта, жизненный цикл аттестации вокруг запуска.
- ABI проверяющего, переносимость и изоляция; вероятно, вместе с будущими работами по предоставлению данных и навыкам (Skills).
- Кэширование аттестации.
- Шаблоны семантического слоя Looker и dbt, где проверяющий переходит от равенства SQL к равенству модели и привязок.

<a id="13-changes-from-v01"></a>

## 13. Изменения относительно v0.1 {#section-13-changes-from-v01}

v0.2 заменяет OKF v0.1 и является увеличением минорной версии согласно §12, кроме двух намеренных несовместимых изменений ниже: они переименовывают или выводят из использования поля v0.1. Читатель v0.2 может читать набор v0.1 с описанными здесь вариантами совместимости.

<a id="131-breaking-changes"></a>

### 13.1 Несовместимые изменения {#section-131-breaking-changes}

- **`timestamp` заменён на `generated.at`.** Последнее изменение содержимого понятия теперь записывается как `generated: { by, at }` (§5.2). Читатели МОГУТ использовать старое `timestamp`, когда `generated` отсутствует.
- **Список `# Citations` в теле заменён на `sources`.** Происхождение перемещено в метаданные (§5.1). Читателям СЛЕДУЕТ читать `sources`; они МОГУТ по-прежнему разбирать старый список `# Citations` в документах v0.1.

<a id="132-additive-changes"></a>

### 13.2 Добавления {#section-132-additive-changes}

Всё перечисленное ниже — добавления: новые необязательные ключи, один новый тип понятия и один новый общепринятый заголовок. Их отсутствие оставляет обычное понятие v0.1.

- Новые группы полей метаданных: `sources` с признаками надёжности каждого источника (`author`, `usage_count`, `last_modified`) и соседним `usage_window`; `generated`, `verified`; `status`, `stale_after` (§5).
- Новый тип понятия `Attested Computation` и его поля вычисления `runtime`, `parameters`, `computation`, `executor`, `attester` (§10).
- Новый общепринятый заголовок тела `# Computation` (§4.2).
- Соглашение об участниках действия для `generated.by` и `verified[].by` (§7).

Всё остальное — структура набора, зарезервированные имена файлов, обязательный `type`, рекомендуемые `title`/`description`/`resource`/`tags`, ссылки между понятиями, файлы оглавления, журналы, мягкие правила соответствия — перенесено без изменений.

## Приложение A: полный пример отчёта о финансовых результатах {#appendix-a-worked-example-an-income-statement}

Один набор, использующий все группы полей, показан как переход с v0.1 на v0.2 для отчёта о финансовых результатах с двумя показателями: выручкой и валовой прибылью.

### Форма v0.1 {#v01-form}

Один документ: оба показателя в одном понятии; SQL в тексте, который агент может прочитать, проигнорировать или переписать; цитаты плоским списком; единственная временная отметка — `timestamp`.

```markdown
---
type: Metric
title: Отчёт о финансовых результатах (финансовый год)
description: Основные показатели отчёта о финансовых результатах за финансовый год.
tags: [finance, income-statement]
timestamp: '2026-05-28T22:53:05+00:00'
---

# Определение
Отчёт о финансовых результатах содержит выручку и валовую прибыль за финансовый год.

# Выручка
Признанная выручка — сумма `amount` по строкам, учтённым за финансовый год:

    SELECT SUM(amount) AS revenue
    FROM finance.recognized_revenue
    WHERE fiscal_year = <year>

# Валовая прибыль
Валовая прибыль по сегментам согласно стандарту распределения затрат:

    SELECT gross_profit FROM fct_income_statement
    WHERE fiscal_year = <year> AND segment = <segment>

# Citations
- https://wiki.acme/finance/fpa-handbook
- https://wiki.acme/finance/revenue-recognition
- https://wiki.acme/finance/cost-allocation
```

### Форма v0.2 {#v02-form}

Два показателя выделены в аттестуемые вычисления, на которые ссылается описательное понятие. Заполнены все группы полей; два вычисления намеренно имеют разные состояния, поэтому один читатель получает два разных вердикта.

```
bundles/finance/
  metrics/income-statement.md      type: Metric  (описывает, ссылается на оба)
  computations/revenue.md          type: Attested Computation  (runtime: bigquery)
  computations/profit.md           type: Attested Computation  (runtime: dbt)
  references/skills/run-on-bq.md, run-dbt.md
  references/attesters/sql-equality.py, dbt-binding.py
```

`metrics/income-statement.md` — читаемый документ; основания доверия к вычислениям находятся в понятиях, на которые он ссылается, а не здесь:

```markdown

type: Metric
title: Отчёт о финансовых результатах (финансовый год)
description: Основные показатели отчёта о финансовых результатах за финансовый год.
tags: [finance, income-statement]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-12-31T00:00:00Z
sources:
  - id: fpa-handbook
    resource: https://wiki.acme/finance/fpa-handbook
    title: Руководство FP&A по отчётности
---

# Определение
Отчёт о финансовых результатах содержит [выручку](../computations/revenue.md)
и [валовую прибыль](../computations/profit.md) за финансовый год согласно
руководству FP&A по отчётности.[^fpa-handbook] Каждый показатель получается
утверждённым вычислением, допускающим аттестацию; это понятие только описывает их.

[^fpa-handbook]: Руководство FP&A по отчётности
```

`computations/revenue.md` — SQL BigQuery, проверенный человеком, актуальный и подтверждённый используемой панелью с признаками надёжности источника:
