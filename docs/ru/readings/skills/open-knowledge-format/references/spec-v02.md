# Open Knowledge Format (OKF)
{:id="open-knowledge-format-okf"}

**Версия 0.2**

OKF — открытый формат представления *знаний*, удобный людям и агентам: метаданных, контекста и отобранных содержательных выводов о данных и системах. Люди могут писать такие документы, агенты — создавать их, организации — обмениваться ими; читать их могут и люди, и агенты.

Формат намеренно минимален: каталог файлов Markdown с блоками метаданных YAML в начале файлов. Реестра схем, центрального органа управления и обязательных инструментов нет. Если вы можете прочитать файл через `cat`, вы можете прочитать OKF; если можете клонировать репозиторий через `git clone`, можете передать набор знаний.

Документ самодостаточен: здесь указано всё необходимое для создания и чтения OKF v0.2. Изменения относительно v0.1 кратко перечислены в §13.

## 1. Мотивация
{:id="1-motivation"}

Представление знаний для AI-агентов быстро развивается, и появляется много несовместимых соглашений. OKF исходит из того, что знания лучше представлять в общедоступных, устоявшихся форматах, которые:

- **Можно читать** людям без специальных инструментов.
- **Можно разбирать** агентам без специализированных SDK.
- **Можно сравнивать** в системе контроля версий.
- **Можно переносить** между инструментами и организациями и сохранять во времени.

Всё чаще набор знаний пишут не один раз для последующего чтения: агенты **непрерывно создают и поддерживают его**. Когда большинство понятий создаётся автоматически, читателю нужны ответы, которые обычное соглашение «Markdown плюс метаданные» не выделяет явно:

1. На основе чего это создано и как проверено? (**Происхождение**.)
2. Насколько этому можно доверять? (**Доверие**.)
3. Верно ли это до сих пор? (**Актуальность**.)
4. Текущая ли это версия? (**Жизненный цикл**.)
5. Получено ли это число именно предписанным способом? (**Подтверждение выполнения вычисления**.)

OKF v0.2 явно описывает происхождение, доверие, жизненный цикл и подтверждение вычислений, сохраняя минимум предписаний. Формат ограничивается небольшим набором структурных соглашений, необходимых, чтобы набор знаний описывал сам себя; всё остальное остаётся на усмотрение автора.

### Цели
{:id="goals"}

1. Определить универсальный формат, который могут записывать **создатели**: люди, агенты и процессы экспорта.
2. Объяснить **потребителям** — агентам, интерфейсам, поисковым индексам и детерминированному коду — как читать документы и переходить между ними.
3. Облегчить **обмен** знаниями между системами и организациями.
4. Стандартизировать небольшой набор полей метаданных, по которым можно **оценить доверие** к набору знаний, поддерживаемому агентами, без предписания среды исполнения.

### Что не входит в задачи
{:id="non-goals"}

- Определение фиксированной классификации типов понятий.
- Предписание инфраструктуры хранения, предоставления данных или запросов.
- Замена предметных схем: Avro, Protobuf, OpenAPI и других. OKF *ссылается* на них, а не включает их в себя.
- Стандарт упаковки или вызова кода, на который ссылается исполнитель или проверяющий вычисление. OKF задаёт интерфейс, а не упаковку.

## 2. Термины
{:id="2-terminology"}

- **Набор знаний**: самодостаточная иерархическая коллекция документов со знаниями; единица распространения. В оригинале — Knowledge Bundle, или bundle.
- **Понятие**: отдельная единица знаний в наборе, представленная одним документом Markdown. Может описывать материальный объект — таблицу, API, абстрактную идею — метрику, бизнес-процесс, либо что-то промежуточное.
- **Идентификатор понятия**: путь файла понятия внутри набора без суффикса `.md`.
- **Блок метаданных**: блок YAML в начале файла Markdown, ограниченный строками `---`. В оригинале — frontmatter.
- **Тело документа**: всё содержимое файла после блока метаданных.
- **Ссылка**: обычная ссылка Markdown между понятиями, выражающая связи помимо неявной иерархии родительских и дочерних документов.
- **Источник**: материал, на основе которого создано понятие; может находиться внутри или вне набора. Записывается в поле `sources`.
- **Происхождение**: совокупность источников, на основе которых создано понятие.
- **Признак надёжности**: объективный факт об отдельном источнике (`author`, `usage_count`, `last_modified`), используемый для оценки доверия. OKF записывает признаки, а не заключение (см. §5.1).
- **Участник**: строка, определяющая, кто или что выполнило действие. Используется соглашение `<producer>/<version>` для агентов, `human:<id>` для людей и `process:<id>` для автоматических процессов (см. §7). В оригинале — actor.
- **Уровень доверия**: уровень, выводимый из поля `verified`: непроверенное, подтверждённое машиной или проверенное человеком понятие (см. §5.3).
- **Вычисление с подтверждением выполнения**: понятие (`type: Attested Computation`), содержащее утверждённый способ вычислить значение, чтобы потребитель мог подтвердить, что значение получено именно его выполнением (см. §10).
- **Исполнитель**: инструкции или код, выполняющие вычисление и возвращающие свидетельство выполнения (см. §10.2). В оригинале — executor.
- **Свидетельство выполнения**: доказательные данные, возвращаемые запуском, со структурой, заданной `executor.receipt`. Это результат исполнения, который не хранится в наборе (см. §10). В оригинале — receipt.
- **Проверяющий вычисление**: детерминированный код без LLM, который проверяет свидетельство выполнения и возвращает заключение (см. §10.2). В оригинале — attester.

## 3. Структура набора
{:id="3-bundle-structure"}

Набор — дерево каталогов с файлами Markdown. Структура каталогов не зависит от предметной области: создатели организуют понятия так, как удобно для фиксируемых знаний.

```
path/to/bundle/
  index.md                      # Необязательно. Список каталога для постепенного знакомства.
  log.md                        # Необязательно. Хронологическая история обновлений.
  <concept>.md                  # Понятие в корне набора.
  <subdirectory>/               # Подкаталоги группируют понятия.
    index.md
    <concept>.md
    <subdirectory>/
      ...
```

Набор МОЖЕТ распространяться как:

- Git-репозиторий: рекомендуется, поскольку он предоставляет историю, сведения об авторстве и сравнение изменений.
- Архив tar или zip с каталогом.
- Подкаталог более крупного репозитория.

### 3.1 Зарезервированные имена файлов
{:id="31-reserved-filenames"}

Следующие имена имеют определённый смысл на любом уровне иерархии и НЕ ДОЛЖНЫ использоваться для документов понятий:

| Имя файла | Назначение |
|---|---|
| `index.md` | Список содержимого каталога. См. §8. |
| `log.md` | История обновлений. См. §9. |

Все остальные файлы `.md` — документы понятий.

Метки остаются самостоятельным элементом формата благодаря полю `tags` (§4.1). OKF не задаёт отдельный файловый формат для группировки документов по меткам; потребитель, которому нужен просмотр по меткам, может сформировать его при чтении, просмотрев метаданные.

## 4. Документы понятий
{:id="4-concept-documents"}

Каждое понятие — файл Markdown в UTF-8 из двух частей:

1. **Блок метаданных YAML**, начинающийся отдельной строкой `---` в начале файла и заканчивающийся отдельной строкой `---`.
2. **Тело Markdown** с содержимым свободной формы.

### 4.1 Блок метаданных
{:id="41-frontmatter"}

```yaml
---
type: <Имя типа>                  # ОБЯЗАТЕЛЬНО
title: <Необязательное название>
description: <Необязательное краткое описание>
resource: <Необязательный канонический URI описываемого объекта>
tags: [<tag>, <tag>, ...]          # Необязательно
# ... группы полей доверия, жизненного цикла, происхождения и вычислений (см. §5, §10)
# ... другие пары ключ/значение, определённые создателем
---
```

**Обязательно:**

- `type`: короткая строка, определяющая вид понятия. Потребители используют её для выбора обработки, фильтрации и представления. Примеры значений: `BigQuery Table`, `BigQuery Dataset`, `API Endpoint`, `Metric`, `Playbook`, `Reference`, `Attested Computation`.

  Значения типов **не регистрируются** централизованно. Создателям СЛЕДУЕТ выбирать описательные и понятные значения; потребители ДОЛЖНЫ корректно переносить неизвестные типы, обычно рассматривая их как обычные понятия.

`type` — единственный ключ, обязательный всегда; понятие, содержащее только `type`, полностью соответствует формату (§11).

**Рекомендуется:**

- `title`: понятное человеку название для отображения. Если отсутствует, потребители МОГУТ вывести его из имени файла.
- `description`: одно предложение, кратко описывающее понятие. Используется генераторами `index.md`, поисковыми фрагментами и предварительным просмотром.
- `resource`: URI, однозначно определяющий объект, описываемый понятием. Отсутствует у понятий об абстрактных идеях, а не физических ресурсах.
- `tags`: список YAML из коротких строк для классификации, не ограниченной иерархией каталогов.

Также могут присутствовать необязательные группы полей **происхождения**, **доверия** и **жизненного цикла** (§5), а для понятий Attested Computation — поля **вычислений** (§10).

**Расширения:** создатели МОГУТ включать любые дополнительные ключи. Потребителям СЛЕДУЕТ сохранять неизвестные ключи при чтении и повторной записи; они НЕ ДОЛЖНЫ отвергать документы с незнакомыми полями.

### 4.2 Тело документа
{:id="42-body"}

Тело использует стандартный Markdown. Создателям СЛЕДУЕТ предпочитать структурированный Markdown — заголовки, списки, таблицы и ограждённые блоки кода — свободной прозе: структура помогает и людям читать, и агентам находить сведения.

Обязательных разделов тела нет. Следующие заголовки имеют **условно закреплённое** значение, и их СЛЕДУЕТ использовать там, где это применимо:

| Заголовок | Назначение |
|---|---|
| `# Schema` | Структурированное описание столбцов или полей объекта. |
| `# Examples` | Конкретные примеры применения, часто в ограждённых блоках кода. |
| `# Computation` | Утверждённое вычисление понятия Attested Computation. См. §10. |

Для привязки отдельных утверждений к внешним источникам используются сноски Markdown с ключами записей `sources`, а не список цитат в теле (§5.1).

### 4.3 Пример: понятие, связанное с ресурсом
{:id="43-example-a-concept-bound-to-a-resource"}

```markdown
---
type: BigQuery Table
title: Заказы покупателей
description: Одна строка на завершённый заказ покупателя по всем каналам.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders, revenue]
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-05-28T14:30:00Z }
---

# Схема

| Столбец | Тип | Описание |
|---|---|---|
| `order_id` | STRING | Глобально уникальный идентификатор заказа. |
| `customer_id` | STRING | Внешний ключ к [покупателям](/tables/customers.md). |
| `total_usd` | NUMERIC | Сумма заказа в долларах США. |
| `placed_at` | TIMESTAMP | Время оформления заказа покупателем. |

# Соединения

Соединяется с [покупателями](/tables/customers.md) по `customer_id`.
```

2. ...

## 5. Происхождение, доверие и жизненный цикл
{:id="5-provenance-trust-and-lifecycle"}

Эти группы метаданных отвечают на вопросы «откуда это взялось», «насколько этому доверять» и «актуально ли это». Все они необязательны. Их отсутствие тоже имеет смысл: непроверенное понятие можно отличить от проверенного, но нельзя отвергать (§11).

### 5.1 Происхождение: `sources`
{:id="51-provenance-sources"}

`sources` записывает материалы, на основе которых создано понятие, внутри или вне набора.

```yaml
sources:
  - id: ga4-schema
    resource: https://developers.google.com/analytics/bigquery/export-schema
    title: Схема экспорта GA4 в BigQuery
    author: team:ga4-docs
    usage_count: 5000
    last_modified: 2026-05-30
usage_window: { from: 2026-06-01, to: 2026-06-30 }
```

Каждая запись `sources`:

- `resource`: ОБЯЗАТЕЛЬНО внутри записи. Указывает либо конкретный объект, который потребитель может открыть: абсолютный URL, путь относительно набора или путь в подкаталог `references/` (§6), либо описание совокупности или области, которое открыть нельзя: например, `все запросы в проекте BigQuery X`.
- `id`: необязательно. Устойчивый ключ для привязки отдельных утверждений (см. ниже). Его СЛЕДУЕТ указывать, если тело ссылается на источник.
- `title`: необязательно. Понятное человеку название источника.
- Необязательные признаки надёжности `author`, `usage_count` и `last_modified`, описанные далее.

**Признаки надёжности источника.** OKF записывает объективные признаки отдельных источников, чтобы потребитель мог оценить доверие к понятию через источники, из которых оно извлечено. Оценка надёжности числом не хранится: она субъективна, непереносима между потребителями и устаревает. Надёжность *выводится* из признаков, как и уровни доверия (§5.3), а не хранится. Каждый признак необязателен и находится в записи `sources`:

- `author`: кто или что создало источник, по соглашению об участниках (§7). Признак авторитетности.
- `usage_count`: сколько раз `resource` использовали — просмотры панели, выполнения запросов, чтения страницы — за `usage_window`. Признак востребованности и активности. Для отдельного объекта это число его использований; для описания области — число использований в этой области, затрагивающих понятие.
- `last_modified`: когда изменился сам источник (`YYYY-MM-DD`). Признак давности, отличный от `generated.at` (§5.2), который фиксирует время написания понятия.
- `usage_window`: записывается один раз рядом с `sources` и задаёт диапазон дат `{ from, to }` для всех `usage_count`. Отдельная запись МОЖЕТ иметь свой `usage_window`, переопределяющий общий.

`usage_count` — грубый признак. По нему можно сравнивать активные и неиспользуемые источники, порядки величин и историю одного источника во времени. Он не подходит для точного ранжирования разных видов источников: выполнение запроса по расписанию и сознательный просмотр панели человеком имеют разный вес. Потребителям СЛЕДУЕТ читать его как признак активности и тенденции, а не как оценку.

Цепочка происхождения выражается ссылками, а не отдельным полем. Когда `resource` указывает на другое понятие OKF, связь происхождения уже существует в графе набора (§6). Поэтому потребитель МОЖЕТ рекурсивно пройти по `sources` этого источника и учитывать их надёжность далее по цепочке. Внешние конечные источники несут только собственные признаки. Более глубокие цепочки — явное внешнее `derived_from` или происхождение данных — не входят в v0.2.

**Привязка отдельных утверждений.** Для привязки конкретного утверждения используйте сноску Markdown, метка которой равна `sources[].id`:

```markdown
Таблица `events_` ежедневно разбивается на таблицы `events_YYYYMMDD`.[^ga4-schema]

[^ga4-schema]: Схема экспорта GA4 в BigQuery
```

Метка сноски — ключ соединения с `sources`. Потребители определяют источник по соответствующей записи, а не разбирают текст сноски. Метки используют ключи, а не позиции (`sources[0]`), потому что агенты постоянно переписывают документы: позиционный индекс незаметно приписывает утверждение другому источнику при перестановке списка, тогда как устойчивый `id` сохраняет связь.

### 5.2 Доверие: `generated` и `verified`
{:id="52-trust-generated-and-verified"}

`generated` фиксирует, как создано текущее содержимое. `verified` фиксирует, кто или что подтвердило содержимое по источникам или `resource`. Эти поля разделены, потому что автор понятия и проверивший его участник могут различаться.

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
```

- `generated.by`: ОБЯЗАТЕЛЬНО внутри `generated`. Участник (§7).
- `generated.at`: дата и время ISO 8601 последнего значимого изменения содержимого. Потребители используют её, чтобы отличить недавнюю правку от устаревшего факта.

```yaml
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

- `verified`: список событий проверки, каждое с `by` (участник) и `at` (дата и время ISO 8601). Несколько записей фиксируют независимые проверки, например подтверждение человеком и ночной процесс. Давность проверки определяет самое позднее `at`.
- `verified` не зависит от `generated.at`: содержимое может меняться без повторного подтверждения, а факты — подтверждаться повторно без пересоздания.
- Единственная проверка МОЖЕТ записываться одним отображением `{ by, at }` без маркера списка. Потребители ДОЛЖНЫ трактовать отдельное отображение как список из одного элемента:

```yaml
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
```

### 5.3 Уровни доверия
{:id="53-trust-tiers"}

Потребители выводят уровень доверия из `verified`, от низшего к высшему:

- Нет ключа `verified` ⇒ **не проверено**.
- `verified` содержит только участников без `human:` ⇒ **подтверждено машиной**.
- `verified` содержит участника `human:<id>` ⇒ **проверено человеком**.

Понятие без метаданных доверия всё равно пригодно для чтения; потребители НЕ ДОЛЖНЫ отвергать его (§11). Уровни доверия — рекомендательные признаки, а не управление доступом.

### 5.4 Жизненный цикл: `status`
{:id="54-lifecycle-status"}

```yaml
status: stable        # draft | stable | deprecated
```

- `draft`: ещё не проверено; возможно, неполно.
- `stable`: значение по умолчанию; готово к использованию.
- `deprecated`: сохранено для ссылок и истории; больше не актуально.

Нет `status` ⇒ `stable`.

### 5.5 Жизненный цикл: `stale_after`
{:id="55-lifecycle-stale_after"}

```yaml
stale_after: 2026-09-23   # абсолютная дата; с этого дня содержимое устарело
```

Необязательно. Абсолютная дата (`YYYY-MM-DD`). Понятие устарело, когда `today >= stale_after`. Абсолютная дата, в отличие от относительного TTL, позволяет решить вопрос простым сравнением дат без обращения ко времени чтения понятия.

## 6. Перекрёстные ссылки и пути
{:id="6-cross-linking-and-paths"}

### 6.1 Ссылки между понятиями
{:id="61-links-between-concepts"}

Понятия МОГУТ ссылаться на другие понятия обычными ссылками Markdown. Поддерживаются две формы:

- **Абсолютная относительно набора:** начинается с `/`, интерпретируется относительно корня набора. Это **рекомендуемая** форма: она устойчива при перемещении документов внутри их подкаталога.

  ```markdown
  Ключ соединения см. в [таблице покупателей](/tables/customers.md).
  ```

- **Относительная:** обычный относительный путь Markdown.

  ```markdown
  См. [соседнее понятие](./other.md).
  ```

Ссылка из понятия A в понятие B утверждает *связь*. Конкретный вид — родитель/потомок, ссылка на материал, соединение, зависимость — передаёт окружающий текст, а не сама ссылка. Потребители, строящие граф, обычно рассматривают все ссылки как направленные рёбра связи без заданного типа.

Потребители ДОЛЖНЫ переносить неработающие ссылки: цель, отсутствующая в наборе, не делает ссылку некорректной; она может обозначать ещё не написанные знания.

### 6.2 Поля со значением пути
{:id="62-path-valued-fields"}

Несколько полей задают путь или URI: `resource`, `sources[].resource`, `computation`, `executor.resource` и `attester.resource` (§10). `sources[].resource` вместо этого может описывать область (§5.1), и тогда не является путём. Каждое поле со значением пути принимает:

- абсолютный URL, например `https://...`;
- путь относительно набора, начинающийся с `/`;
- относительный путь, например `../computations/revenue.md`.

### 6.3 Соглашение о `references/`
{:id="63-the-references-convention"}

Подкаталог `references/` по соглашению содержит копии внешних материалов, инструкции запуска или код как самостоятельные понятия внутри набора. Источники, исполнители и проверяющие вычисления часто указывают туда, например на `references/attesters/revenue.py`. Это соглашение об именовании, а не требование.

## 7. Соглашение об участниках
{:id="7-actor-convention"}

Поля, фиксирующие личность (`generated.by`, `verified[].by`), используют единое соглашение об участниках:

- `<producer>/<version>` для агентов и инструментов, например `reference_agent/gemini-2.5-pro`.
- `human:<id>` для человека, например `human:ahormati`.
- `process:<id>` для автоматического процесса, например `process:finance-nightly`.

Потребители, определяющие доверие (§5.3), ориентируются на префикс `human:`. Поэтому создатели ДОЛЖНЫ использовать его для содержимого, написанного или подтверждённого человеком.

## 8. Индексные файлы
{:id="8-index-files"}

Файл `index.md` МОЖЕТ находиться в любом каталоге, включая корень набора. Он перечисляет содержимое каталога для **постепенного знакомства**: человек или агент сначала видит, какие материалы доступны, а затем открывает отдельные документы.

Индексные файлы не содержат блока метаданных, кроме одного случая: корневой `index.md` МОЖЕТ содержать ключ `okf_version` (§12). Тело содержит один или несколько разделов, каждый из которых группирует понятия под заголовком:

```markdown
# Заголовок раздела или группы

* [Название 1](relative-url-1) - краткое описание пункта 1
* [Название 2](relative-url-2) - краткое описание пункта 2

# Другой раздел

* [Подкаталог](subdir/) - краткое описание подкаталога
```

Записям СЛЕДУЕТ включать описание из метаданных понятия, на которое они ссылаются. Создатели МОГУТ автоматически генерировать `index.md`; потребители МОГУТ формировать его на лету при отсутствии файла.

## 9. Файлы журнала
{:id="9-log-files"}

Файл `log.md` МОЖЕТ находиться на любом уровне иерархии и фиксировать историю изменений соответствующей области. Формат — плоский список записей, сгруппированных по датам, от новых к старым:

```markdown
# Журнал обновлений каталога

## 2026-05-22
* **Обновление**: Добавлена ссылка на таблицу BigQuery для [метрик покупателей](/tables/customer-metrics.md).
* **Создание**: Создана [инструкция Dataplex](/playbooks/dataplex.md).

## 2026-05-15
* **Инициализация**: Создана базовая структура каталогов.
```

Заголовки дат ДОЛЖНЫ использовать форму ISO 8601 `YYYY-MM-DD`. Записи журнала — обычный текст; начальное выделенное слово (`**Update**`, `**Creation**`, `**Deprecation**`) является соглашением, а не требованием.

## 10. Понятие вычисления с подтверждением выполнения
{:id="10-attested-computations-concept"}

Понятие Attested Computation содержит не только смысл значения, но и утверждённый способ его *вычислить*, чтобы потребитель мог подтвердить, что агент выполнил предписанное вычисление, а не придумал своё. Происхождение (§5.1) отвечает на вопрос «откуда взялось утверждение», а подтверждение выполнения — «получено ли число предписанным способом». OKF записывает вычисление и средства его проверки; сам формат ничего не исполняет.

### 10.1 Вычисление — отдельное понятие
{:id="101-a-computation-is-its-own-concept"}

Утверждённое вычисление — самостоятельное понятие с `type: Attested Computation`. Понятие, которому нужно значение (`Metric`, `BigQuery Table`), ссылается на него обычной ссылкой Markdown (§6). Отдельное понятие обосновано тремя свойствами:

- **`runtime` определяет смысл `parameters`.** В зависимости от среды параметр — переменная привязки SQL, переменная dbt или аргумент Python. Размещение `runtime` и `parameters` в одном блоке метаданных делает правила привязки очевидными.
- **Одно вычисление — много потребителей.** Одно вычисление может обслуживать метрику, понятие панели и отчёт; как самостоятельное понятие оно описывается один раз и используется повторно.
- **Состояние доверия относится к отдельному вычислению.** `verified`, `stale_after` и один `attester` описывают одну сущность. Выручка, прибыль и маржа проверяются и подтверждаются независимо: это три понятия, а не три записи в одном блоке метаданных.

### 10.2 Поля контракта
{:id="102-contract-fields"}

Контракт — поля верхнего уровня в метаданных понятия. Помимо групп происхождения, доверия и жизненного цикла (§5), понятие Attested Computation содержит:

- `runtime`: ОБЯЗАТЕЛЬНО для этого типа. Единственное поле, определяющее способ запуска вычисления, а значит — как исполнитель и проверяющий трактуют его и что означают `parameters`. Примеры: `bigquery`, `postgres`, `dbt`, `python`, `Looker`.
- `parameters`: список именованных параметров с типами, значения для которых может задать агент. Каждая запись: `{ name, type, required }`. Правила привязки зависят от `runtime`.
- `computation`: необязательно. Путь (§6.2) к файлу с вычислением, используемый вместо блока кода в теле (см. §10.3). Отсутствует ⇒ вычисление находится в блоке под `# Computation` в теле.
- `executor`: способ запуска вычисления. `resource` указывает инструкции запуска или код; запускающий участник — агент или детерминированный код потребителя — следует им. `receipt` объявляет поля, которые запуск должен вернуть: доказательные данные для проверки, например BigQuery `job_id` и реально выполненный SQL.
- `attester`: детерминированная проверка. `resource` указывает код без LLM, принимающий свидетельство выполнения и возвращающий заключение. Предназначен для запуска на стороне потребителя.

Что находится за `resource` — навык агента, скрипт, контейнер — вопрос упаковки. OKF задаёт интерфейс, а не упаковку (§1).

```markdown
---
type: Attested Computation
title: Выручка за финансовый год
description: Признанная выручка за финансовый год по определению финансовой службы.
status: stable
runtime: bigquery
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/skills/run-on-bq.md
  receipt: [job_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Правила признания выручки
---

# Computation

    SELECT SUM(amount) AS revenue
    FROM finance.recognized_revenue
    WHERE fiscal_year = @year

Вычисление привязывает только объявленные `parameters` согласно правилам
признания выручки.[^rev-policy]

[^rev-policy]: Правила признания выручки
```

### 10.3 Вычисление
{:id="103-the-computation"}

Предоставьте вычисление одним из двух способов:

- **В теле:** единственный ограждённый блок кода под `# Computation`. Подходит для короткого вычисления, проверяемого вместе с контрактом.
- **В файле:** задайте `computation` путём (§6.2), не добавляя блок кода в тело. Подходит для длинного или сгенерированного вычисления либо вычисления, уже хранящегося в настоящем файле для инструментов вне OKF.

```yaml
runtime: bigquery
computation: references/computations/lib/revenue.sql
parameters:
  - { name: year, type: integer, required: true }
```

Агент МОЖЕТ задавать только *значения* объявленных `parameters`; он НЕ ДОЛЖЕН писать или редактировать вычисление. Привязка значений параметров к `computation` и получение исполняемого результата — задача потребителя. Проверяющий независимо повторяет ту же привязку, чтобы сравнить её с реально выполненным кодом. Поскольку сравнивается развёрнутый, скомпилированный результат из свидетельства выполнения (`executed_sql`, `compiled_sql`), переписанный запрос, подменённый файл вычисления или изменённая зависимость не проходят проверку. Типизированный интерфейс, допускающий только параметры, превращает вопрос «выполнилось ли утверждённое вычисление» в механическое сравнение, а не субъективное решение.

### 10.4 Понятия, использующие вычисление
{:id="104-concepts-that-use-a-computation"}

Документ редко описывает одно вычисление. Обзор отчёта о прибылях и убытках, обсуждающий выручку, прибыль и маржу, остаётся одним читаемым понятием и ссылается на отдельное Attested Computation для каждого показателя:

```markdown
---
type: Metric
title: Выручка
description: Признанная выручка за финансовый год.
tags: [finance, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
---

# Определение

Признанная выручка — сумма `amount` по строкам, отнесённым к финансовому году;
её получает [вычисление выручки](../computations/revenue.md).
```

Поскольку каждое вычисление — отдельное понятие, выручка может быть актуальна, а прибыль — уже за пределами `stale_after`; каждый запуск подтверждается отдельно. Совместное размещение — выбор каталогов (`computations/` с `index.md`), а не блока метаданных.

### 10.5 Как потребитель использует это (информационный раздел)
{:id="105-how-a-consumer-uses-it-informative"}

Этот подраздел информационный, а не нормативный. Результаты исполнения ниже **не** хранятся в наборе.

1. **Найти** по `type: Attested Computation` — признаку в метаданных, который можно вынести в `index.md`. Потребитель открывает понятие напрямую или по ссылке из использующего его понятия.
2. **Загрузить** контракт из метаданных и вычисление из тела или файла, указанного в `computation`.
3. **Задать параметры:** агент предоставляет значения объявленных параметров.
4. **Выполнить:** исполнитель запускает вычисление с привязанными значениями и возвращает свидетельство выполнения со структурой `executor.receipt`.
5. **Подтвердить:** потребитель запускает проверяющий код на свидетельстве выполнения. Код подтверждает происхождение: выполненное вычисление совпадает с `computation`, к которому привязаны заявленные параметры, а не с SQL, написанным агентом. Он также подтверждает точность: показанное значение совпадает с достоверным источником свидетельства, повторно прочитанным по идентификатору задания, а не взятым из текста агента.
6. **Принять решение:** отказаться показывать значение при неуспешном подтверждении; предупредить или отказать при `today >= stale_after`. При успехе показать заключение, например ссылку на журнал задания, чтобы основание доверия было видно.

### 10.6 Проверка документа и подтверждение выполнения
{:id="106-verification-versus-attestation"}

`verified` (§5.2) и подтверждение выполнения различаются и существуют одновременно:

- `verified` подтверждает, что *определение* по-прежнему соответствует правилам. Проверка относится к документу, проводится медленно и записывается в набор.
- Подтверждение выполнения проверяет, что один *запуск* получил значение утверждённым способом. Проводится для каждого вызова во время исполнения и не хранится в наборе.

Понятие с устаревшим определением всё ещё может успешно пройти подтверждение выполнения. Недавно проверенное определение всё равно требует подтверждения каждого запуска. Поэтому нужны оба механизма.

## 11. Соответствие формату
{:id="11-conformance"}

Набор **соответствует** OKF v0.2, если:

1. Каждый незарезервированный файл `.md` в дереве содержит разбираемый блок метаданных YAML.
2. Каждый блок метаданных содержит непустое поле `type`.
3. Каждый файл с зарезервированным именем (`index.md`, `log.md`), если присутствует, следует структуре §8 и §9 соответственно.

Если присутствуют группы полей доверия, жизненного цикла, происхождения или вычислений, создателям СЛЕДУЕТ следовать §5–§10, а потребителям:

- Потребители ДОЛЖНЫ трактовать отдельное отображение `verified` как список из одного элемента (§5.2).
- Потребители НЕ ДОЛЖНЫ отвергать понятие из-за отсутствия любой необязательной группы (§5.3).
- СЛЕДУЕТ выводить уровень доверия и устаревание только из указанных здесь полей, а неуспешное подтверждение выполнения СЛЕДУЕТ показывать, а не молча отбрасывать (§10.5).

Потребителям СЛЕДУЕТ считать все остальные ограничения мягкими рекомендациями. В частности, потребители НЕ ДОЛЖНЫ отвергать набор из-за:

- Отсутствия необязательных метаданных.
- Неизвестных значений `type`.
- Неизвестных дополнительных ключей метаданных.
- Неработающих перекрёстных ссылок.
- Отсутствия файлов `index.md`.

## 12. Версионирование
{:id="12-versioning"}

Этот документ задаёт OKF версии **0.2**. Редакции имеют версии `<major>.<minor>`:

- Изменение **минорной** версии вводит совместимые дополнения: новые необязательные поля или новые условные заголовки разделов.
- Изменение **мажорной** версии может нарушать совместимость: переименовывать обязательные поля или менять зарезервированные имена файлов.

Наборы МОГУТ объявлять целевую версию через `okf_version: "0.2"` в метаданных корневого `index.md`: это единственное место, где `index.md` может содержать блок метаданных. Потребителям, не понимающим объявленную версию, СЛЕДУЕТ попытаться прочитать набор в меру своих возможностей, а не отказывать.

### Рассмотрено и отложено
{:id="considered-and-deferred"}

Следующее намеренно оставлено будущей редакции:

- Полный протокол исполнения: форматы передачи свидетельства выполнения и заключения, а также жизненный цикл подтверждения вокруг запуска.
- ABI проверяющего кода, переносимость и изоляция, вероятно вместе с будущей работой над предоставлением данных и навыками агентов.
- Кеширование подтверждений выполнения.
- Шаблоны семантического слоя (Looker, dbt), где сравнение переходит от равенства SQL к равенству модели и привязки параметров.

## 13. Изменения относительно v0.1
{:id="13-changes-from-v01"}

v0.2 заменяет OKF v0.1 и повышает минорную версию по §12, кроме двух намеренных несовместимых изменений ниже: они переименовывают или упраздняют поля v0.1. Потребитель v0.2 может прочитать набор v0.1 с описанными здесь резервными способами чтения.

### 13.1 Несовместимые изменения
{:id="131-breaking-changes"}

- **`timestamp` заменён на `generated.at`.** Последнее изменение содержимого понятия теперь записывается как `generated: { by, at }` (§5.2). Потребители МОГУТ использовать старый `timestamp`, если `generated` отсутствует.
- **Список `# Citations` в теле заменён на `sources`.** Происхождение перемещено в метаданные (§5.1). Потребителям СЛЕДУЕТ читать `sources`; они МОГУТ продолжать разбирать старый список `# Citations` в документах v0.1.

### 13.2 Совместимые дополнения
{:id="132-additive-changes"}

Все следующие изменения — дополнения: новые необязательные ключи, один новый тип понятия и один новый условный заголовок. При их отсутствии остаётся обычное понятие v0.1.

- Новые группы метаданных: `sources` с признаками надёжности каждого источника (`author`, `usage_count`, `last_modified`) и соседним `usage_window`; `generated`, `verified`; `status`, `stale_after` (§5).
- Новый тип `Attested Computation` и его ключи `runtime`, `parameters`, `computation`, `executor`, `attester` (§10).
- Новый условный заголовок тела `# Computation` (§4.2).
- Соглашение об участниках для `generated.by` и `verified[].by` (§7).

Всё остальное перенесено без изменений: структура набора, зарезервированные имена файлов, обязательный `type`, рекомендуемые `title`/`description`/`resource`/`tags`, перекрёстные ссылки, индексные файлы, журналы и допускающие необязательные данные правила соответствия.

## Приложение A: подробный пример — отчёт о прибылях и убытках
{:id="appendix-a-worked-example-an-income-statement"}

Один набор, использующий все группы полей, представлен как миграция отчёта с v0.1 на v0.2. В отчёте два показателя: выручка и валовая прибыль.

### Форма v0.1
{:id="v01-form"}

Один документ: оба показателя в одном понятии, SQL в тексте, который агент может прочитать, проигнорировать или переписать; цитаты — плоский список, единственная временная отметка — `timestamp`.

```markdown
---
type: Metric
title: Отчёт о прибылях и убытках за финансовый год
description: Основные показатели отчёта о прибылях и убытках за финансовый год.
tags: [finance, income-statement]
timestamp: '2026-05-28T22:53:05+00:00'
---

# Определение
Отчёт о прибылях и убытках показывает выручку и валовую прибыль за финансовый год.

# Выручка
Признанная выручка — сумма `amount` по строкам, отнесённым к финансовому году:

    SELECT SUM(amount) AS revenue
    FROM finance.recognized_revenue
    WHERE fiscal_year = <year>

# Валовая прибыль
Валовая прибыль по сегментам согласно стандарту распределения затрат:

    SELECT gross_profit FROM fct_income_statement
    WHERE fiscal_year = <year> AND segment = <segment>

# Citations
- https://wiki.acme/finance/fpa-handbook
- https://wiki.acme/finance/revenue-recognition
- https://wiki.acme/finance/cost-allocation
```

### Форма v0.2
{:id="v02-form"}

Два показателя разделены на вычисления с подтверждением выполнения, на которые ссылается описывающее их понятие. Все группы полей заполнены. Два вычисления намеренно находятся в разных состояниях, чтобы один потребитель получил два заключения.

```
bundles/finance/
  metrics/income-statement.md      type: Metric  (описывает и ссылается на оба)
  computations/revenue.md          type: Attested Computation  (runtime: bigquery)
  computations/profit.md           type: Attested Computation  (runtime: dbt)
  references/skills/run-on-bq.md, run-dbt.md
  references/attesters/sql-equality.py, dbt-binding.py
```

`metrics/income-statement.md` — читаемый документ; доверие к вычислениям относится к объектам его ссылок, а не к этому документу:

```markdown
---
type: Metric
title: Отчёт о прибылях и убытках за финансовый год
description: Основные показатели отчёта о прибылях и убытках за финансовый год.
tags: [finance, income-statement]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-12-31
sources:
  - id: fpa-handbook
    resource: https://wiki.acme/finance/fpa-handbook
    title: Руководство по отчётности FP&A
---

# Определение
Отчёт о прибылях и убытках показывает [выручку](../computations/revenue.md) и
[валовую прибыль](../computations/profit.md) за финансовый год по руководству
FP&A.[^fpa-handbook] Каждый показатель получается утверждённым вычислением,
выполнение которого можно подтвердить; это понятие только описывает их.

[^fpa-handbook]: Руководство по отчётности FP&A
```

`computations/revenue.md` — BigQuery SQL, проверен человеком, актуален и подтверждён активно используемой панелью с признаками надёжности:

  - { name: year, type: integer, required: true }

  resource: references/attesters/sql-equality.py

sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition

    author: team:finance-fpa
    last_modified: 2026-04-02
  - id: exec-rev-dash

Признанная выручка по правилам признания выручки,[^rev-policy] подтверждённая
