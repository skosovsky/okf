# T12. Доказать совместимость между инструментами и с чужими bundle

fixtures/interoperability уже содержит замороженный внешний корпус; fixtures/v02 — положительные, исторические и отрицательные данные. Использовать ту же модель provenance: URL, ревизия, digest, лицензия, разрешённые изменения. Чужие тесты и примеры переносить только после проверки условий лицензии; для поведения достаточно своего минимального fixture.

**Общий корпус.** Три группы: собственные граничные случаи T01–T07; пример upstream Appendix A и опубликованный bundle; небольшой реальный срез Crossplane catalog со ссылками и ресурсами. Сохранить собственные входные bytes и явно описать ожидаемые ID, пути, tier, stale/current, diagnostics и результат записи. При невозможности включить чужие файлы — воспроизводимая проверка по pinned checkout и собственный аналог для offline CI.

**Две стороны обмена.** Открыть чужой bundle в нашем CLI, MCP и viewer; перестроить индекс и проверить семантику и сохранность расширений. Создать наш bundle, передать его зафиксированному внешнему reader/validator и сверить результат. Сверять с нормативным текстом при разногласиях. Выбрать небольшой набор независимых проверок: upstream validator, Rust W4G1 или Python ekar-is. Зафиксировать версии, команды и область сравнения. Соблюсти различие между base conformance и предупреждениями чужого линтера.

**Приёмка релизного кандидата.**

- На одном снимке и одном as-of получить Go/CLI JSON, stdio MCP, результат Action, граф и viewer. Сопоставить семантику общих полей, причины пропуска, разрешение путей и целевые ID; различия форм представления описать.
- Проверить новые и прежние версии, legacy proofs, явный отказ при конфликте ревизий, отсутствие потерь и повторяемость миграции. Пройти все пять бинарников, установочные манифесты, три skills, EN/RU сайт и offline demo.
- Из чистого tracked checkout выполнить go test ./..., проверки из .github/workflows/ci.yml и action-integration.yml, сборку пакета и сайта, сценарии из docs/release-engineering.md. Проверить производительность на существующих benchmark относительно baseline при изменении обхода графа или discovery. Не удалять локальные файлы пользователя ради чистого прогона.
- Выдать итоговую матрицу «требование → задача → команда/тест → результат → артефакт/ревизия». Поломки и непройденные проверки перечислить с владельцем. Заявление о полной поддержке требует закрытых нормативных и интеграционных строк.
