# T10. Показать смену правила в поиске и viewer

Уже есть retrieval, viewer, двуязычный examples/project-knowledge, scripts/build-project-demo.sh, scripts/build-viewer-demo.sh и benchmarks/retrieval. Расширить знакомый пример изменения срока доставки с 24 до 48 часов.

1. Дать пользователю пройти путь «найти правило → открыть источник → увидеть смысловую правку после ревью → найти замену по старой ссылке». Развести дату проверки, срок пересмотра и статус. Показать старую подпись в истории. Добавить root title/description/license и один небольшой пример расширения с данными, разрешёнными к публикации.
2. Отразить состояние в карточке поиска и в деталях viewer. Поясняющий текст открывается по необходимости. При просмотре исторического документа показать ссылку на замену; исключить зацикливание. Сверить обычные и current-запросы, исходный и конечный ID, совпадения по секциям и snippets.
3. Для разработчика дать отдельные граничные fixtures: одноимённые относительные пути и внешнее вычисление с отсутствующей целью. Пользовательский quickstart остаётся одним коротким сценарием.

**Приёмка.** По одному и тому же запросу на фиксированную дату CLI, MCP и offline HTML находят ожидаемое правило и источник. Прогнать retrieval benchmark с прежним baseline и отдельно добавить version-aware ожидания. Сгенерировать обе локали demo, открыть локально, проверить поиск, переходы, мобильную ширину, клавиатуру, подписи состояния и отсутствие сетевой зависимости. Зафиксировать исходный bundle и команду генерации.
